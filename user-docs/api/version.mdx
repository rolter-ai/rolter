`GET /api/v1/version` answers three questions about the build in one document:
which rolter this control plane is, whether a newer stable release exists, and
which of its subsystems ship as experimental. The dashboard reads it once per
session — for the small *v0.2.0 available* hint beside the version in its
footer, and for the experimental markers it draws in the navigation — so no
browser ever calls GitHub itself and a deployment does not leak per-user egress.

The answer comes from a check the control plane runs on its own schedule — once
at boot and every six hours — against
`https://api.github.com/repos/rolter-ai/rolter/releases/latest`, bounded by a
5-second timeout. The endpoint only ever reads the last successful result; it
never triggers a check.

## Request

```http
GET /api/v1/version
Authorization: Bearer <session or admin token>
```

Any authenticated caller may read it — a viewer with no membership anywhere
included. The `version` capability that `GET /api/v1/rbac/matrix` publishes is
read-only for every authenticated caller and writable by nobody: this is a fact
about the deployment, not about any tenant. An anonymous request is refused with `401`.

## Response

```json
{
  "current": "0.1.0",
  "latest": "0.2.0",
  "release_url": "https://github.com/rolter-ai/rolter/releases/tag/v0.2.0",
  "update_available": true,
  "checked_at": "2026-09-05T08:12:44.913Z",
  "enabled": true,
  "experimental": [
    {
      "id": "mcp_tool_groups",
      "stability": "experimental",
      "note": "tool-group manifests are stored and published to MCP-aware clients, but the proxy does not enforce group membership as an access boundary",
      "nav_keys": ["tool-groups"]
    }
  ]
}
```

| Field | Type | Meaning |
|---|---|---|
| `current` | string | the version this control plane was built as (the Cargo workspace version, which release-plz maintains) |
| `latest` | string or `null` | the latest stable release the last successful check reported; `null` until one has succeeded |
| `release_url` | string or `null` | the release page to send an operator to |
| `update_available` | boolean | `latest` is strictly newer than `current` by semantic-version order |
| `checked_at` | RFC 3339 or `null` | when the last successful check completed |
| `enabled` | boolean | whether the check runs at all; `false` when `ROLTER_UPDATE_CHECK=false` |
| `experimental` | array | the subsystems this build ships as experimental; see below |

### States

The dashboard treats every state except "update available" as "show the plain
version". These are the shapes it can meet:

| Situation | `enabled` | `latest` | `update_available` |
|---|---|---|---|
| check disabled (`ROLTER_UPDATE_CHECK=false`) | `false` | `null` | `false` |
| still checking, or offline / rate-limited so far | `true` | `null` | `false` |
| current or newer than the latest release | `true` | set | `false` |
| an older build | `true` | set | `true` |

An air-gapped control plane that has not opted out is indistinguishable from
one still checking: `enabled: true`, everything else empty. Nothing is logged
above `debug`, and nothing is retried more eagerly than the six-hour schedule.

### Version order

Comparison follows semantic versioning. A `v` prefix on the tag is ignored and
build metadata (`+…`) is dropped. Pre-releases are handled explicitly:

- the check only ever reports a **stable** `latest` — a pre-release tag is
  treated as a malformed answer and ignored;
- a pre-release `current` (`0.2.0-rc.1`) sees `update_available: true` for the
  `0.2.0` it precedes;
- a `current` ahead of the latest release — a dev build — reports `false`.

## Experimental subsystems

Not every part of Rolter is equally settled. A subsystem listed in
`experimental` **may change shape or be removed in a minor release** — a
documented exemption from the compatibility promise the rest of the surface
makes. It is not a warning about quality, support or reliability, and it does
not mean the subsystem is turned off: everything listed is enabled and usable.

| Field | Type | Meaning |
|---|---|---|
| `id` | string | stable identifier for the subsystem; never renamed once published |
| `stability` | string | always `experimental` today. Sent explicitly so a reader never has to infer the level from list membership |
| `note` | string | what specifically is unfinished, in one sentence, safe to render verbatim |
| `nav_keys` | string[] | the dashboard navigation entries this subsystem appears under. Empty when it has no screen of its own — a gateway surface such as `/v1/realtime`, or a cross-cutting concept such as labels |

Only the exceptions travel. A subsystem that is **absent** from the array is
stable, and `"stability": "stable"` is never sent: absence is the signal, which
is why the dashboard renders nothing for the overwhelming majority of screens.

The list is a compile-time constant, so it is identical for every caller, never
varies with a deployment's configuration, and changes only when you upgrade
Rolter. An empty array is a valid and expected answer for a build with nothing
outstanding, and the array is served whether or not the update check is enabled.

## Turning it off

Set `ROLTER_UPDATE_CHECK=false` on the control plane. The endpoint keeps
answering, with `enabled: false` and nothing else from the *check* filled in, so
a dashboard built against a checking deployment renders the same on an opted-out
one. `current` and `experimental` are unaffected — neither needs the network,
and an air-gapped deployment still needs to know what its build ships as
experimental. The
same variable silences the `rolter` CLI's stderr notice; see
[Environment variables](/configuration/environment-variables#update-check).

Rolter gives you two complementary levers for controlling how much your gateway spends and how fast it moves traffic: **spend budgets** block requests once a cumulative USD ceiling is reached, and **rate limits** reject requests that exceed per-minute throughput thresholds. Both systems operate across the same scopes — the four-level tenancy hierarchy (org → team → project → key) plus the two cost-attribution dimensions a key rolls up to (business unit, customer) — and apply a most-restrictive-wins policy when multiple rules match a single request.

<Warning>
  Budgets and rate limits both require Redis (`REDIS_URL`). Rolter uses Redis for distributed counters so limits remain accurate across multiple gateway instances. Without Redis, both budgets and rate limits **fail open** — they are not enforced and all requests pass through.
</Warning>

## Step 1 — Define model prices

Before budgets can track spend, Rolter needs to know the cost of each model's tokens. Add one `[[model_prices]]` block per model with rates per million tokens, denominated in the currency you name (USD by default).

<ParamField path="model" type="string" required>
  The public model name as it appears in your `[[routes]]` configuration.
</ParamField>

<ParamField path="input_per_mtok" type="float">
  Cost in USD per million input (prompt) tokens.
</ParamField>

<ParamField path="output_per_mtok" type="float">
  Cost in USD per million output (completion) tokens.
</ParamField>

<ParamField path="cached_input_per_mtok" type="float">
  Cost per million cache-hit input tokens. Defaults to `input_per_mtok` when omitted.
</ParamField>

<ParamField path="currency" type="string" default="USD">
  Currency the rates above are denominated in. Any code works — ISO-4217, a crypto unit, an internal credit — as long as `[currency.rates]` can convert it to the base currency.
</ParamField>

```toml rolter.toml
[[model_prices]]
model = "gpt-4o"
input_per_mtok = 2.5
output_per_mtok = 10.0
cached_input_per_mtok = 1.25

[[model_prices]]
model = "claude"
input_per_mtok = 3.0
output_per_mtok = 15.0
```

<Info>
  Models without a `[[model_prices]]` entry log a `cost_usd` of `0` and an `unpriced` flag of `1` per request. They can still be used, but their spend does not count toward any budget. Add a price entry for every model you want budgets to track, and see [Unpriced traffic](#unpriced-traffic) below for how to make that gap fail closed instead of open.
</Info>

### Pricing in another currency

Spend and budgets accumulate in a single **base currency**. A model priced in anything else is converted at a rate you configure, once, when the gateway loads its config — so pricing in EUR while budgeting in USD is exact rather than off by the FX rate.

```toml rolter.toml
[currency]
base = "USD"
rates = { EUR = 1.09, GBP = 1.27 }

[[model_prices]]
model = "mistral-large"
input_per_mtok = 2.0
output_per_mtok = 6.0
currency = "EUR"     # charged into the USD budget at 1.09
```

A rate is how many base units one unit of that currency is worth. The base itself is always `1.0` and needs no row. Codes are open strings rather than a fixed list, so adding `BTC` or an internal credit unit means adding a rate row — no new release required.

<Warning>
  A model priced in a currency with no rate is a **config error**, not a warning: the gateway refuses to start and the dashboard refuses the write. Charging face value would bill the wrong number and charging zero would bill nothing, so neither is offered as a fallback.

  Rates are operator-supplied and static, which is deliberate — Rolter must run air-gapped, so it never reaches out to an FX feed.
</Warning>

### What the dashboard offers

The currency chooser on a model's pricing section is your rate table, not a built-in list: it shows the base currency followed by every code in `[currency.rates]`. Adding `rates = { RUB = 0.011 }` makes `RUB` selectable on the next control-plane restart, with no dashboard release involved.

That set is read from `GET /api/v1/currency`, which answers from the bootstrap config rather than the database — the store keeps a currency per model price and no rate table, so this is the one place that knows what a deployment can convert. It is also exactly the set the CRUD API accepts, so the chooser cannot offer a code the save would reject.

A price already stored in a code that is no longer in the table still displays, flagged as unconvertible on both the Pricing screen and the model sheet. Its spend is missing from base-currency totals and budgets until you add the rate back.

Every amount the dashboard renders — LLM Logs, budget cards, team cards, the spend tiles — is formatted in the base currency from that same endpoint, so a deployment budgeting in EUR reads `€` rather than a hardcoded `$`. Model prices are the exception: they are shown in the currency the price row was written in, which is what you typed. Amounts, dates and counts all follow the dashboard's language rather than the browser's, so the separators in a number never disagree with the copy beside it.

## Step 2 — Configure spend budgets

A spend budget blocks incoming requests with **HTTP 402** once the cumulative cost for a scope reaches `limit_usd` within the configured period. Add one `[[budgets]]` block per scope you want to cap.

<ParamField path="scope" type="string" required>
  The scope level this budget applies to. One of `org`, `team`, `project`, `key`, `business_unit`, or `customer`.
</ParamField>

<ParamField path="id" type="string" required>
  The UUID of the entity at the chosen scope (org ID, team ID, project ID, virtual key ID, business unit ID, or customer ID).
</ParamField>

<Note>
  `business_unit` and `customer` are not part of the org → team → project chain: they are the [cost-attribution dimensions](/observability/logs-and-cost) a virtual key rolls its spend up to, so a budget on one caps everything attributed to it regardless of which project the traffic came through. The control plane API and the dashboard's **Budgets & Limits** screen accept all six scopes; in the dashboard, picking one of these two lists your org's business units or customers rather than asking for a UUID.
</Note>

<ParamField path="limit_usd" type="float" required>
  The maximum cumulative spend in USD for the period before requests are blocked.
</ParamField>

<ParamField path="period" default="monthly" type="string">
  The window over which spend accumulates. One of `monthly`, `daily`, or `total`. `monthly` and `daily` windows reset automatically; `total` is a lifetime cap that never resets.
</ParamField>

```toml rolter.toml
# Hard ceiling for the entire org — resets on the first of each month
[[budgets]]
scope = "org"
id = "org-uuid"
limit_usd = 500.0
period = "monthly"

# Tighter daily cap for a specific project
[[budgets]]
scope = "project"
id = "project-uuid"
limit_usd = 20.0
period = "daily"

# Lifetime cap on a single virtual key
[[budgets]]
scope = "key"
id = "vk-uuid"
limit_usd = 100.0
period = "total"
```

When a request's scope chain matches multiple budget rules (e.g. both an org budget and a project budget), Rolter applies **most-restrictive-wins**: the request is blocked as soon as any matching budget is exhausted.

<Tip>
  Set an org-level budget as a hard ceiling to protect against unexpected runaway costs, then add project- or key-level budgets to allocate share to individual teams or clients.
</Tip>

### Unpriced traffic

A budget can only block spend it can see. A model with no `[[model_prices]]` entry accrues **zero**, so it can never exhaust a budget however much is served — the control fails open on exactly the models you most recently added and are least likely to have priced.

`unpriced_policy` is the deliberate decision about that. It is set deployment-wide, since it governs what the gateway may serve at all rather than the state of any one counter, and an individual budget may then ask for something stricter — see [Per-budget override](#per-budget-override):

```toml
unpriced_policy = "block"   # ignore (default) | warn | block
```

| policy | behaviour |
| --- | --- |
| `ignore` | Serve it and accrue nothing. Budgets silently do not cover it. |
| `warn` | Serve it, but log the model once per hour so an unenforceable budget names itself. |
| `block` | Refuse at admission with **HTTP 402** and error code `model_unpriced`, naming the model. The check runs before the upstream call, so no tokens are spent on traffic no budget would ever have counted. |

```json
{
  "error": {
    "message": "model 'llama-3.1-8b' has no price, so its cost cannot be counted against a budget. This deployment, or a budget that applies to this key, is configured to refuse traffic it cannot account for; set a price for this model to serve it.",
    "type": "invalid_request_error",
    "code": "model_unpriced",
    "param": "model"
  }
}
```

`ignore` is the default so that upgrading Rolter cannot start refusing traffic for a deployment that has not priced its models yet. Once every routed model has a price, `block` never fires and turns the budget into a guarantee rather than a best effort.

<Note>
  Unlike budgets themselves, `unpriced_policy` needs no Redis — being unpriced is a property of the config, not of a counter. It is enforced even when budgets are failing open.
</Note>

<Note>
  The built-in `fake-llm` model is answered by the gateway before any price lookup, so `block` never makes it unreachable.
</Note>

#### Per-budget override

`unpriced_policy` on `[gateway]` is the deployment's floor. A single budget can
ask for something **stricter** than that floor without imposing it on the rest
of the deployment:

```toml
[[budgets]]
scope = "team"
id = "platform"
limit_usd = 500
period = "monthly"
unpriced_policy = "block"   # this team refuses what it cannot account for
```

In the dashboard the same field is on **Limits → Add budget**, as *Unpriced
traffic*. Leaving it at *Inherit deployment setting* is what every budget does
by default, and is how every budget created before this field existed behaves.

Resolution is **most-restrictive-wins** (`ignore` < `warn` < `block`) across
everything that applies to the request — the deployment setting and every
budget matching the request's scope chain. Two consequences follow, and both
are deliberate:

- **A budget can only tighten.** A project budget set to `ignore` does not undo
  an org budget set to `block`, the same way it cannot raise the org's spend
  cap. A control a narrower scope could loosen would not be a control.
- **The deployment setting is a floor, not merely a fallback.** If the
  deployment is set to `block`, no budget can opt back into serving unpriced
  traffic.

A request that matches no budget at all is answered by the deployment setting,
unchanged.

<Note>
  The override lives on the budget row, so it works for budgets defined in the
  database through the control plane as well as for `rolter.toml` ones — a
  setting only `rolter.toml` could reach would silently do nothing for the
  deployments that use the dashboard.
</Note>

## Step 3 — Configure rate limits

A rate limit rejects requests with **HTTP 429** (plus a `Retry-After` header) when the number of requests or tokens in the trailing one-minute window exceeds the cap. Add one `[[rate_limits]]` block per scope you want to throttle.

<ParamField path="scope" type="string" required>
  The scope level this limit applies to. One of `org`, `team`, `project`, `key`, `business_unit`, or `customer`.
</ParamField>

<ParamField path="id" type="string" required>
  The UUID of the entity at the chosen scope.
</ParamField>

<ParamField path="rpm" type="integer">
  Maximum requests per minute. Omit to leave request count uncapped.
</ParamField>

<ParamField path="tpm" type="integer">
  Maximum tokens per minute (prompt \+ completion combined). Omit to leave token throughput uncapped.
</ParamField>

```toml rolter.toml
# Cap a single virtual key to 600 req/min and 150k tok/min
[[rate_limits]]
scope = "key"
id = "vk-uuid"
rpm = 600
tpm = 150000

# Cap an entire project to 2000 req/min (no token cap)
[[rate_limits]]
scope = "project"
id = "project-uuid"
rpm = 2000
```

<Note>
  At least one of `rpm` or `tpm` must be set. A `[[rate_limits]]` block with neither field never actually caps anything — Rolter will warn about this during config validation.
</Note>

Like budgets, rate limits follow **most-restrictive-wins** across the scope chain. A per-key limit can throttle a client well below the project-level ceiling, and an org-level limit acts as a global backstop.

## How counters work

Rolter maintains sliding-window counters in Redis — one counter per (scope, id, window bucket) combination. Each counter is updated atomically on every request, so limits remain accurate even when you run multiple gateway instances behind a load balancer. The `Retry-After` response header on a 429 tells the client how many seconds to wait before the trailing window slides enough to admit the next request.

## Complete example

The following snippet brings together pricing, a budget, and a rate limit for a production setup:

```toml rolter.toml
# Per-model pricing
[[model_prices]]
model = "gpt-4o"
input_per_mtok = 2.5
output_per_mtok = 10.0
cached_input_per_mtok = 1.25

# Org-wide monthly spend cap
[[budgets]]
scope = "org"
id = "acme-org-uuid"
limit_usd = 500.0
period = "monthly"

# Tighter cap for the analytics project
[[budgets]]
scope = "project"
id = "analytics-project-uuid"
limit_usd = 50.0
period = "monthly"

# Per-key throughput limit for a high-volume client
[[rate_limits]]
scope = "key"
id = "analytics-vk-uuid"
rpm = 600
tpm = 150000
```

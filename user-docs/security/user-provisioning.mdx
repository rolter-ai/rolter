Rolter speaks SCIM 2.0, so your identity provider can create, update, and deactivate Rolter accounts — and push its groups — without anyone touching the dashboard. You issue a provisioning token for the org, paste it into the IdP's SCIM connector, and the IdP does the rest on its own schedule.

The direction of control matters: **the identity provider drives provisioning, Rolter receives it.** The dashboard never calls the SCIM endpoints. What you manage in **Governance → User Provisioning** is the credential the IdP authenticates with — issuing one, seeing when it last synced, and revoking it.

## What a provisioning token is

A provisioning token is an opaque bearer credential scoped to exactly one org.

<Info>
The token carries the tenant. There is no org id anywhere in the SCIM URL, which means a token issued for one org physically cannot address another org's users — even if the IdP is misconfigured.
</Info>

Issuing, listing, and revoking tokens all require the **admin** role on the org (see [RBAC](/security/rbac)). A member or viewer sees an explanation instead of the token list.

## Wire up an identity provider

<Steps>
  <Step title="Issue a token">
    Open **Governance → User Provisioning** and choose **Issue token**. Name it after the connector it will live in — `Okta production`, `Entra staging` — because that name is the only thing that identifies it afterwards.
  </Step>

  <Step title="Copy the token immediately">
    The plaintext value is displayed exactly once, in the panel that opens right after creation. Rolter stores only a peppered SHA-256 digest of it, so **the value cannot be displayed or recovered later** — not by you, not by support, not from a database dump. If you lose it, issue a new token and revoke the old one.
  </Step>

  <Step title="Configure the connector">
    In your identity provider, set the SCIM base URL to `https://your-rolter-host/scim/v2` and the authentication mode to HTTP header / bearer token, using the value you just copied. Enable *create users*, *update user attributes*, and *deactivate users* — and *push groups* if you plan to drive roles from group membership.
  </Step>

  <Step title="Push a test user">
    Assign one person to the Rolter application in the IdP and run a sync. They appear under **Governance → Users**, and the token's **Last sync** column updates on the next request.
  </Step>
</Steps>

## What provisioning does and does not grant

A provisioned account is deliberately minimal:

- It joins the org with the **viewer** role, merely for existing. SCIM decides *who exists*; anything beyond a read comes from a group mapping you wrote (see [Map groups to teams](#map-groups-to-teams)).
- It has **no local password**. A `password` attribute sent by the IdP is ignored rather than stored — provisioned accounts are SSO-shaped by construction.
- Deactivating a user through SCIM also drops their live sessions, so a leaver disabled in the IdP is logged out of Rolter rather than merely blocked from signing in again.
- A SCIM `DELETE` deactivates the account and removes the org's identity mapping, but keeps the underlying user row: its memberships and audit trail have to outlive any one IdP. Re-provisioning the same person adopts the existing account instead of creating a duplicate.

Every provisioning action is written to the [audit log](/observability/logs-and-cost) with the token id as the actor, since the change was made by a machine and not by a person.

## Supported operations

| Operation | Endpoint | Notes |
| --- | --- | --- |
| List / search users | `GET /scim/v2/Users` | Supports the `userName eq "value"` filter that IdPs use for reconciliation; other filters are rejected explicitly rather than silently ignored |
| Create user | `POST /scim/v2/Users` | Idempotent — a replayed create returns a `uniqueness` conflict instead of a second account |
| Read user | `GET /scim/v2/Users/{id}` | |
| Replace user | `PUT /scim/v2/Users/{id}` | |
| Patch user | `PATCH /scim/v2/Users/{id}` | The `active` attribute, in both the `path: "active"` and bare-value shapes IdPs send |
| Deprovision | `DELETE /scim/v2/Users/{id}` | Deactivates and unmaps; the account row survives, and its group-granted roles go with the identity |
| List / search groups | `GET /scim/v2/Groups` | Supports the `displayName eq "value"` filter |
| Create group | `POST /scim/v2/Groups` | Idempotent — a replayed create returns a `uniqueness` conflict |
| Read group | `GET /scim/v2/Groups/{id}` | |
| Replace group | `PUT /scim/v2/Groups/{id}` | Replaces the member list wholesale |
| Patch group | `PATCH /scim/v2/Groups/{id}` | Member add / remove / replace in every shape IdPs send, plus `displayName` and `externalId` |
| Delete group | `DELETE /scim/v2/Groups/{id}` | Removes the group and everything it granted |

## Map groups to teams

A group arriving from your identity provider grants nothing on its own. **You** decide what it is worth, by writing a mapping — the identity provider never gets to name a role.

**Governance → User Provisioning** carries a **Group mappings** panel under the token list. Type the group's display name, pick where the role applies — the whole organization, a team, or a project — pick the role, and press **Map group**. The scope list covers the whole organization: every team, and every project in any of those teams grouped under the team it belongs to, so a mapping onto a project outside the team the scope switcher currently shows needs no detour through the switcher. An organization with no teams yet says so, and offers only itself. The panel lists every mapping the org has with its scope and role, and removing one asks first, because it withdraws that role from everyone in the group. Until a mapping exists the panel says so plainly: the groups your IdP pushes grant nothing, and every provisioned account stays a viewer.

The same thing over the API:

```bash
curl -X POST https://your-rolter-host/api/v1/orgs/$ORG_ID/scim-group-mappings \
  -H "Authorization: Bearer $ADMIN_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"group_name": "platform", "role": "member", "team_id": "'$TEAM_ID'"}'
```

- `group_name` is the group's **display name** as your IdP shows it.
- `role` is one of `admin`, `member`, `viewer` — the same three roles [RBAC](/security/rbac) defines. Nothing else is mappable.
- Name a `team_id` or a `project_id` to grant at that scope; omit both to grant at the org.
- The scope must belong to the same org. A mapping cannot reach another tenant's team, whatever the IdP sends.

This is the same model [single sign-on](/security/single-sign-on) uses for its group mappings, so you only learn it once.

<Info>
Mappings key on the group's display name. If you rename a group in the identity provider, rewrite the mapping too — otherwise the old name simply stops matching and the roles it granted are withdrawn on the next sync.
</Info>

You can write a mapping before the group has ever been pushed. Creating or deleting one takes effect immediately for whoever is already in that group, rather than waiting for the next sync.

## What a sync does to roles

Every group change recomputes the affected people's provisioning-granted roles from scratch:

- Running the same sync twice changes nothing.
- Removing someone from a group revokes exactly what that group gave them, right away.
- A role **you** granted by hand — in the dashboard, through the API, or through an invitation — is never touched by a sync. Manual and provisioned grants coexist.
- Deleting a group, or deprovisioning a user, withdraws the roles involved in the same request.

<Warning>
Because a mapping is a way to grant a role, creating or deleting one requires the **admin** role on the org — the same bar as granting a role directly.
</Warning>

## Rotating and revoking a token

Revocation takes effect on the very next request — the token is resolved from the database on every call, so there is no cache to wait out.

<Warning>
Revoking a token stops the sync. It does **not** touch the accounts that token already provisioned: nobody is deactivated, nobody is logged out, and no membership is removed. Those accounts simply stop receiving updates from the IdP until you point it at a new token.
</Warning>

To rotate without a gap in coverage:

1. Issue a second token and copy it.
2. Update the connector in the identity provider to use the new value.
3. Run a sync and confirm the new token's **Last sync** timestamp moves.
4. Revoke the old token.

If you need to cut off an identity provider immediately — a compromised connector, for example — revoke the token first and deactivate the affected accounts from **Governance → Users** separately. Revocation alone is not a way to lock people out.

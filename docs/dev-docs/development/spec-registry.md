# External specification registry

rolter claims compatibility with a long list of things it did not write: OpenAI's
REST API, Anthropic's dated Messages API, Gemini's three surfaces, MCP, SCIM, OIDC,
OTLP, the OpenTelemetry GenAI conventions and so on. Before #907 the evidence for
each claim was spread across comments, ADRs and dependency versions, and nobody
could answer "which revision, how much of it, proven by what" without an audit.

The registry is the answer, kept in one file:
[`crates/rolter-core/specifications.toml`](../../../crates/rolter-core/specifications.toml).

## What reads it

| Consumer                                  | What it takes                                                                                                                                                                                                         |
| ----------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `rolter_core::spec_registry`              | The schema (every table denies unknown keys), `Registry::validate`, and `annotate_openapi`                                                                                                                            |
| the gateway's and control plane's OpenAPI | `externalDocs` plus `x-rolter-spec-refs`, `x-rolter-conformance` and `x-rolter-reviewed-at` on every operation a record names, and on every gateway `components/schemas` entry a record lists under `gateway_schemas` |
| `docs/user-docs/api/specifications.mdx`   | Its tables, between the `spec-registry:begin` and `spec-registry:end` markers, generated by `just gen-specs`                                                                                                          |
| `spec-ref` comments in the code           | The record ids, checked to exist                                                                                                                                                                                      |

The file is embedded with `include_str!`, so a binary serves its claims without the
tree, and it lives inside `rolter-core` so `cargo package` carries it. The OpenAPI
extensions are only ever added to rolter's own documents: no vendor request or
response payload carries a rolter field.

## Records

A `[[spec]]` is one external specification:

| Field                                    | Meaning                                                                                                                                         |
| ---------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| `id`                                     | Stable, lowercase, `-`-separated. Published in `x-rolter-spec-refs`, so never renamed                                                           |
| `category`                               | `ai-api`, `translation`, `wire-format`, `transport`, `identity`, `telemetry` or `api-description`                                               |
| `authority`, `title`                     | Who publishes it and what it is called                                                                                                          |
| `url`                                    | The official primary source, HTTPS                                                                                                              |
| `related`                                | Further official sources (streaming grammar, errors, a superseded RFC); HTTPS                                                                   |
| `contract`                               | How the source versions itself: `dated`, `semver`, `major-only`, `living`, `rfc`, `standard` or `vendor-preview`                                |
| `version`                                | The revision implemented or sent on the wire. Required by every contract except `living` and `vendor-preview`, shaped by it, and never `latest` |
| `pinned`                                 | A full 40-hex upstream commit the version was audited at, where one exists                                                                      |
| `reviewed_at`                            | When the claim was last checked against the source, `YYYY-MM-DD`                                                                                |
| `conformance`                            | `native-passthrough`, `translation-subset`, `transport-only`, `extension` or `partial`                                                          |
| `gateway_endpoints`, `control_endpoints` | `METHOD /path` in OpenAPI path-template form                                                                                                    |
| `gateway_schemas`                        | `components/schemas` names in the gateway's document                                                                                            |
| `modules`                                | The files that implement the claim, relative to the repository root                                                                             |
| `supported`, `omissions`, `deviations`   | What is honoured, what is left out, and where rolter departs on purpose                                                                         |
| `tests`                                  | `crates/<path>.rs` or `crates/<path>.rs::<test name>`: the evidence                                                                             |
| `notes`                                  | Anything else a reader needs                                                                                                                    |

A `[[provider]]` is one `ProviderKind`: `kind`, `authority`, `url`, an example
`base`, the `dialects` (spec ids) it speaks, its `auth` scheme (`bearer`,
`x-api-key`, `api-key` or `x-goog-api-key`), the `primary_path` rolter sends its
primary request to, a `conformance` (here `provider-profile` is allowed: an
auth/path profile over an OpenAI-shaped transport; so is `unverified`, for a kind
with no located public API reference, which the dashboard marks as unverified
through `GET /api/v1/provider-kinds` and `spec_registry::is_unverified`), `reviewed_at`, `notes` and
`tests`. `auth` and `primary_path` are not just documentation: a test holds them
to `ProviderKind::auth_header` and `primary_upstream_path`.

Each distinct auth/path profile also has a conformance fixture in
`crates/rolter-gateway/tests/provider_profiles.rs` (#3336): a request and a
response shaped after the vendor's documentation, replayed through the gateway
against a mock upstream mounted at the documented base. Each case records its
`source`: `Fetched(date)` (Azure, Bedrock, Vertex, the Gemini OpenAI shim, Groq,
Mistral, DeepSeek, and GigaChat from the OpenAPI file its reference pages are
built from, #3488) means the base, path, credential header and request were read
from the documentation page (`doc`) on that date (#3445); `Recalled` (no case
today) means they were written from memory and not checked against the page,
and a kind whose fixture
is only recalled does not claim `provider-profile` in its record:
`no_provider_profile_rests_on_a_recalled_fixture_only` in
`crates/rolter-core/src/spec_registry.rs` reads the cases' `source` from
`provider_profiles.rs` and fails, naming the record, for a `provider-profile`
record whose cited fixtures include no `Fetched` one or name a case the file
does not have (#3495). The
response bodies are illustrative in every case. A recalled case is a regression
guard for the profile rolter sends, not evidence about the vendor. It checks the
path the upstream receives, the header the credential travels in, and that the
response reaches the client whole, vendor extensions included. A kind that
shares a profile with one of them (every hosted kind whose base ends in `/v1`)
is covered by that profile's case; a new profile gets a case and lists it under
its record's `tests`. A kind whose record says "Unverified" in `notes` has no
fixture on purpose: no public API reference was found, and a fixture written
from a guess would be evidence of nothing.

`[native] gateway_endpoints` lists the gateway's own endpoints (`/healthz`,
`/docs`, …), which implement no external specification. A route is either there
or named by a record, never both.

## Versions, honestly

- **Record what is true today.** Where rolter relays bytes it does not read, the
  claim is `transport-only`, and it changes when the code starts reading them:
  the MCP transport record became `partial` once the gateway applied tool
  groups to every JSON-RPC call, yet still says `version = "forwarded"`,
  because the gateway neither reads nor negotiates `MCP-Protocol-Version`.
- **No invented SemVer.** OpenAI's REST API is `major-only` `v1`: it evolves by
  backward-compatible additions, and its type system has no finer version to
  record. `reviewed_at` carries the date instead. rolter does not consume
  OpenAI's published OpenAPI artifact, so no commit of it is pinned.
- **Protocol versions are not crate versions.** OTLP is recorded as the proto
  release the `opentelemetry-proto` crate vendors; the GenAI conventions as the
  `semantic-conventions` release they were audited against (`v1.41.0`, the last
  one carrying the gen-ai registry before it moved to
  `semantic-conventions-genai`), with rolter's local operation values as
  deviations. A test in `crates/rolter-gateway/src/genai.rs` fails when the
  gateway emits a key the record does not list.
- **A runtime constant only when it reaches the wire.**
  `rolter_core::probe::ANTHROPIC_VERSION` exists because rolter sends it; it is
  also the default of `[compatibility] anthropic_version`, and
  `the_anthropic_version_has_one_source` holds both to the `anthropic-messages`
  record. Health probes send the constant rather than the operator's pin, and the
  record says so as a deviation. The test also reads the default
  `config-file.mdx` states. A database-backed deployment does not use the
  `config.rs` default at all: it reads the stored compatibility policy, whose
  column default `0039_compatibility_policy.sql` seeds with the same literal.
  Bumping `ANTHROPIC_VERSION` therefore also needs a new migration that moves
  the stored default (and, if wanted, rows still on the old value); migrations
  are append-only, so 0039 itself never changes. A metadata-only
  `SPEC_VERSION` constant would go stale with nothing to notice.

## `spec-ref` comments

At a parser, translator, adapter or deliberate deviation, point at the record
rather than copying its URL:

```rust
// spec-ref: gemini-generate-content
fn openai_to_gemini(...)
```

or `// spec-ref: a, b` on its own line just below a module's `//!` doc block (a plain comment, so rustdoc does not render it as prose). The marker is followed by one or
more ids separated by commas. Keep a direct link beside the code only where the
subtlety is in one section of the source (`RFC 9110 §7.6.1`).

## Checks

All offline, all in the `nextest / doctests` job of `quality.yml`, so `ci-ok`
covers them:

| Test                                                                                       | Fails when                                                                                                        |
| ------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------- |
| `rolter-core` `spec_registry::tests::the_embedded_registry_is_valid`                       | a rule above is broken: a non-HTTPS source, a versioned record without a version or with `latest`, a bad endpoint |
| `rolter-core` `spec_registry::tests::provider_records_match_how_rolter_reaches_each_kind`  | a kind's recorded auth header or primary path differs from the code, or a kind has no record                      |
| `rolter-core` `spec_registry::tests::the_anthropic_version_has_one_source`                 | the probe constant, the configured default and the record disagree                                                |
| `rolter-core` `tests/spec_registry.rs`                                                     | a cited module or test does not exist, a `spec-ref` names no record, or the generated docs are stale              |
| `rolter-gateway` `openapi::tests::every_route_is_in_the_specification_registry`            | a gateway route has no record, or a record claims a route that is gone                                            |
| `rolter-gateway` `openapi::tests::every_documented_operation_carries_its_provenance`       | a documented operation lacks its `externalDocs` and `x-rolter-*` provenance                                       |
| `rolter-control` `openapi::tests::registry_endpoints_are_documented_with_their_provenance` | a control-plane endpoint a record names is undocumented or unannotated                                            |

The route check reads the `.route(` calls in the body of `build_router` in
`crates/rolter-gateway/src/lib.rs`, the only place gateway routes are added
today. Routes attached through `.merge()` or `.nest()`, or built in another
function, are not seen: adding one means extending
`routed_endpoints()` in `crates/rolter-gateway/src/openapi.rs` first. A route
whose path is a constant rather than a literal fails the test until that
function resolves it.

Reproduce with `cargo nextest run -p rolter-core -p rolter-gateway -p rolter-control spec_registry openapi genai`.

## Changing something the registry describes

The maintenance matrix in `AGENTS.md` has the row. In short: a new endpoint,
provider kind, translation, wire version or semantic attribute changes the
record, its tests and the generated docs in the same PR. Run `just gen-specs`
after editing the file; it rewrites the generated tables and runs
`just fmt-docs`, which aligns them (the freshness check ignores alignment).
The registry is taplo-formatted like every other TOML file.

## Spec drift: research for a scheduled check

#907 asks whether the registry can drive an informational workflow that notices
when an upstream source changes. The design below is what a prototype should
implement; it is not built yet (#3337).

**Signal per source.** Compare the most stable signal a source offers, never a
page's raw bytes:

| Source shape                                                                     | Signal                                                                                                                        |
| -------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------- |
| A git repository (`opentelemetry-proto`, semantic conventions, `b3-propagation`) | the newest release tag, or the commit a branch points at (`git ls-remote`), against `pinned`                                  |
| A dated protocol (Anthropic, MCP)                                                | the newest dated revision the versioning page lists, against `version`                                                        |
| A changelog (OpenAI)                                                             | the newest entry date, against `reviewed_at`                                                                                  |
| An RFC                                                                           | the `Obsoleted by` / `Updated by` header on rfc-editor.org                                                                    |
| A living documentation page                                                      | `ETag` / `Last-Modified` when present, else a digest of the page's main content after stripping navigation, scripts and dates |

**Noise.** Living vendor pages change layout weekly. Only the last row of the
table digests a page, and only its extracted main content; a change there opens
nothing on its own until it persists across two runs.

**Report.** One Actions summary row per changed source: the record id, old and
new signal, the primary URL, and the record's endpoints, modules and tests, so a
reviewer knows where to look. The raw signals are uploaded as an artifact.

**Follow-up.** One tracking issue per record, found by a fixed title
(`spec drift: <id>`) so a second run comments on it rather than opening another.
A draft PR is safe only for a change that is deterministic and generated (a
pinned commit moving with no claim changing); everything else needs a person.

**Acknowledging.** Bumping `reviewed_at` (and `version` or `pinned`) in the
registry is the acknowledgement: the next run compares against the new values.
Deferring is a comment on the tracking issue; the issue stays open.

**Running it.** `schedule` plus `workflow_dispatch`, never `pull_request`, and
never in `ci-ok`'s `needs:`: a vendor outage or a changed page must not fail a PR
or a release. `permissions: contents: read` plus `issues: write` for the issue
step only, SHA-pinned actions, no secrets beyond `GITHUB_TOKEN`, a timeout and a
retry with backoff per fetch, and a source that cannot be fetched is reported as
unavailable rather than as drift.

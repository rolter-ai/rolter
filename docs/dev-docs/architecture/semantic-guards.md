# Semantic guard policies

Issue [#459](https://github.com/rolter-ai/rolter/issues/459). User-facing page: `docs/user-docs/security/semantic-guard-policies.mdx`. Streaming decision: [ADR-0037](../adr/2026-10-27-semantic-guard-streaming.md).

## What it is

A semantic guard is a classifier spoken to over the guardrail webhook contract (`rolter_core::guardrail_webhook`), or one the gateway runs in process (`kind = "local"`, #3329, [ADR-0039](../adr/2026-10-28-local-semantic-classifier.md)): it judges a request (`pre_call`) or a response (`post_call`) by meaning and answers `allow`, `block`, `transform` or `annotate`, optionally with scored `categories`. Several providers can be enabled; a **policy** scoped to the deployment, an org, a project, a route or a virtual key picks which of them judge a request and holds their scores to thresholds.

Guards decide; sanitizers transform. The boundary with the neighbouring subsystems:

| Subsystem                                          | Does                                             | Runs                               |
| -------------------------------------------------- | ------------------------------------------------ | ---------------------------------- |
| built-in rules (`rolter_core::guardrails`)         | regex/builtin detectors: annotate, block, redact | in process, first                  |
| semantic guards (this page)                        | decide by meaning: allow, block, flag, transform | external or local, after the rules |
| PII sanitizer (`rolter_core::pii_sanitizer`, #848) | replace entities with placeholders, restore them | external, after the guards         |
| payload-capture redaction (#1835)                  | mask secrets in captured log payloads            | at capture, never on the wire      |

The guards never see restored PII on the response side (the sanitizer's response leg runs last in `DeliveryPolicy::apply`), and the sanitizer never receives content a guard blocked.

## Layout

- `crates/rolter-core/src/semantic_guards.rs` — the model: `SemanticGuardsConfig` (`[semantic_guards]`: `providers`, `policies`), `GuardrailPolicy`, `PolicyScope`, `ViolationAction`, `StreamingStrategy`, validation (`SemanticGuardsConfig::validate`, `policy_field_problems` shared with the control plane), `CompiledSemanticGuards` (built once per snapshot) and `ScoredDecision` (the strict answer parser).
- `crates/rolter-gateway/src/guardrail_webhook.rs` — the transport: one bounded call with retries, and `CallFailure` naming every way a call can produce no verdict.
- `crates/rolter-gateway/src/local_classifier.rs` — the `local` kind: the `rolter-linear/1` model (`LinearModel`: tokenizer, FNV-1a feature hashing, logistic heads), `classified_text`, and `LocalClassifiers`, the per-gateway registry of loaded models (by digest, in an `ArcSwap`) and the `local_concurrency` semaphore. At start `AppState::assemble` calls `configure` (read and install); on a snapshot the watcher first awaits `preload`, which reads missing models on the blocking pool, and `AppState::reload` then calls `apply`, which installs from memory only, before the snapshot is published.
- `crates/rolter-gateway/src/semantic_guards.rs` — the runtime: `SemanticGuard::check` runs one stage of a resolved policy and folds the answers into a `Verdict`; `stream_text` assembles a buffered SSE response for the providers.
- `crates/rolter-gateway/src/handlers.rs` — the pre-call stage in `RequestCtx::guardrail_webhook`, the stream refusal in `RequestCtx::admit_semantic_leg`, and `SemanticLeg` in `DeliveryPolicy` / `stream_response` for the response stage (live, cached and buffered-stream bodies alike).
- `crates/rolter-gateway/src/realtime.rs`, `realtime_guard.rs` — client events go through the `pre_call` providers; a session whose policy has a `post_call` provider is refused.
- `crates/rolter-control/src/guardrail_policies.rs` — CRUD, `guardrail_policy` capability; `guardrails.rs` serves the `semantic` view in `GET /api/v1/guardrails/effective` and refuses deleting a provider a policy lists.
- Store: `guardrail_providers.kind`, `model_path`, `model_sha256` (`0190`, which also limits the `url` check to webhooks; the table's `config_version` trigger is `0053`), `guardrail_policies`, `guardrail_policy_providers` (`0133`–`0135`), `GuardrailRepo::*_policy`, `PostgresConfigStore::load_semantic_guards`, `merge_semantic_guards` in `rolter-store/src/lib.rs`.
- Dashboard: `ui/src/pages/GuardrailPolicies.tsx`, `GuardrailProviders.tsx`, `ui/src/lib/guardrail-enforcement.ts`.

## Resolution

`CompiledSemanticGuards::from_config(semantic_guards, guardrail_webhook)` keeps the enabled providers (the legacy webhook first, when enabled) and indexes enabled policies by `(scope, scope_id)`. `resolve` walks `PolicyScope::PRECEDENCE` (key, route, project, org, deployment) against the request's `ScopeIds` and route model and returns the first hit. The winner **replaces** the broader policies — no merging — so the policy in force is one row, and thresholds, `on_violation` and `streaming` come from it alone. This mirrors plugin precedence in other gateways (Kong applies the single most specific plugin configuration).

No hit falls back to the implicit policy of the **unattached** providers: enabled providers that no policy lists, enabled or paused. "Paused" counts so that pausing a policy cannot widen its providers to every request. The implicit policy has no thresholds and blocks only on an explicit `block`, which is exactly the pre-#459 single-webhook behaviour; it is labelled `default`.

The store keeps one enabled policy per scope (`guardrail_policies_one_enabled_per_scope`), and `SemanticGuardsConfig::validate` checks the same for the file, so the index is never ambiguous.

## One stage

`SemanticGuard::check` runs the policy's providers for the stage in their listed order:

1. Bound the body (`bounded_payload`, `max_body_bytes`) and post the envelope with `policy` and, for a buffered stream, `streamed: true`.
2. No verdict (`CallFailure`: refused, timeout, connect, overloaded `429`/`503`, other status, unreadable or **unparsable** body) → that provider's `failure_mode`: `fail_open` continues, `fail_closed` returns `Block`. An unparsable answer used to read as `allow`; it now follows the failure mode, so a fail-closed provider that breaks refuses rather than waves through. Only timeout, connect, overload and body failures are retried.
3. An explicit `block` blocks.
4. Scores are judged before a transform: a violation blocks under `on_violation = block`, or adds one `policy_flagged:<policy>` event under `annotate`.
5. A `transform` replaces the body the next provider sees — except on a buffered stream, which is withheld (it cannot be re-encoded).

Every call records `rolter_guardrail_provider_latency_ms{provider}` and one `rolter_guardrail_policy_decisions_total{policy,provider,stage,outcome}`; every violation one `rolter_guardrail_policy_violations_total{policy,category,action}` with the category bounded by `CompiledPolicy::category_label` (a configured name or `other`). The events `check` appends land in the row's `guardrail_events` on both stages: the request stage's directly, the response stage's through `DeliveryPolicy::apply`'s `PolicyEvents` (#3330, see [observability.md](observability.md)). Nothing in this path logs, counts or returns content.

## Local providers (ADR-0039)

`SemanticGuard::check` dispatches on `GuardrailWebhookConfig::kind`: `Webhook` → `consult`, `Local` → `LocalClassifiers::classify`, `Unknown` → `CallFailure::Unsupported`, which is resolved as `fail_closed` whatever the provider says, so a kind a newer control plane sends never stops judging silently. Everything after the answer — thresholds, events, metrics, failure modes — is shared.

`classify_flagged` extracts the text on the async side (`bounded_text`: every string outside `STRUCTURAL_KEYS`, bounded to `GuardrailWebhookConfig::scored_bytes`, which is `max_scored_bytes` or 8 × `max_body_bytes`, held to `MAX_SCORED_BYTES` (16 MiB) and `MAX_SCORED_WINDOWS` (64) windows either way, and whether it had to cut; `validate` refuses an explicit `max_scored_bytes` past either), refuses a cut text under `on_truncated = "fail_closed"` (or an `Unknown` value) with `CallFailure::Truncated` before anything is scored, looks the model up by `model_sha256` (missing → `CallFailure::Model`), waits for a permit of the per-gateway semaphore for at most `timeout_ms` (none → `Overloaded`), then scores it on the blocking pool holding the permit, the remaining budget bounding the join (`Timeout`). `LinearModel::score_windows` scores the text in `windows` of `max_body_bytes`, each overlapping the next by an eighth of a window, at least `MIN_WINDOW_OVERLAP` (256 bytes) and at most half a window, each cut on a character boundary, and keeps every category's highest score (#3513). It returns `Classified { answer, truncated }`; `SemanticGuard::check` opens a `guardrails.local` span (`provider`, `truncated`) around the call and, for a cut text, counts `rolter_semantic_local_truncated_total{provider}` (`Metrics::observe_local_truncated`) and pushes `semantic_truncated:<provider>` into the row's events, whatever the answer. `Truncated`, like `Unsupported`, resolves as `fail_closed` whatever the provider's `failure_mode` says, so it also leaves `provider_error:<provider>`. The Postgres registry persists both settings (`0230_guardrail_provider_truncation.sql`), the control API validates them with the same bounds, and `provider_from_row` maps them into the snapshot; the existing provider-table trigger bumps `config_version` on each write. `OnTruncated` is an enum of the snapshot with an `Unknown` fallback read as `fail_closed` (`on_truncated` kind). The answer is `allow` with every category's sigmoid score; the policy's thresholds do the blocking. `max_retries` and `auth` do not apply; `GuardrailWebhookConfig::validate` refuses a local provider with a url, an auth, no `model_path` or a malformed `model_sha256`, and `operator_url_problems` skips local providers.

Models are read only by `configure` (startup), `preload` (on the blocking pool, before a reload) and the background retry (`retry_missing`, on the blocking pool): a regular file only, at most 64 MiB, the SHA-256 checked against the pin, then parsed with the bounds in `local_classifier.rs` (`MAX_BUCKETS`, `MAX_CATEGORIES`, `MAX_WEIGHTS`, `MAX_NGRAMS`; a bias or weight must be finite as an `f32`, and scores are summed in `f64`, so no sum is infinite or NaN). Every read goes through `read_all` (#3512): each model is read on a thread of its own (`rolter-model-read`, not the blocking pool) and the batch waits on the threads' channels until one shared deadline, `MODEL_READ_DEADLINE` (30 s; `set_reader` swaps the reader and the deadline in tests). A read still running then is abandoned as `ModelError::Deadline`, which is transient, so the watcher awaiting `preload` (and the retry, and `configure` at startup) never waits longer than the deadline. A stuck thread cannot be cancelled, so `start_read` keeps its path in `in_flight` until the read returns (`InFlightGuard`, released before the answer is sent) and refuses another read of that path meanwhile as `ModelError::InFlight`, also transient: a hung mount holds one thread per path, however many reloads and retries ask, and `MAX_IN_FLIGHT_READS` (8) caps the reads running at once across paths, aliases of one file included (`InFlight` too). An abandoned read that returns is logged; a model it loaded (the reader checked the pin) goes into `late` by digest and wakes the retry, and `read_all` takes a digest from `late` instead of starting a read, so a mount slower than the deadline still loads one retry later. `apply` drops `late` entries no configuration wants. A digest already loaded is reused, so a reload re-reads nothing that did not change; a failure is logged at `error` and the provider resolves through its failure mode. Each apply records the providers it wants (`Registry::wanted`); `spawn_retries`, started by `rolter_gateway::run`, re-reads the missing ones on the blocking pool with backoff from `RETRY_FIRST` (1 s) doubling to `RETRY_CAP` (60 s), and `install` adds a model only while the applied configuration still names its digest. Only a `ModelError::is_transient` failure (`Read`, `Root`: an I/O error) is retried; any other (a wrong digest, `OutsideRoot`, a malformed or non-regular file) is recorded in `given_up` under the generation of the apply it failed for (`load_missing` records the next one, since `preload` runs before `apply`), and `retryable` skips it until another configuration is applied, which `preload` reads again anyway. An apply whose wanted set differs bumps `wanted_epoch`; the retry task waits with `sleep_until` against the `Notify`, and an epoch change restarts its wait at `RETRY_FIRST`. Every registry write (`apply`, `install`) holds `writing` and goes through `publish`, which refreshes `ModelStates` (provider name → loaded), shared with `Metrics` as the `rolter_local_classifier_models{provider,state}` gauge, and wakes the retry task when something is missing (#3452). `apply` keeps the previous generation's models beside the new ones until the next apply, so a request still holding the previous snapshot finds its model. A cap change swaps the semaphore; in-flight calls keep the old one's permits. The default cap is half the CPUs, at least one, since the blocking pool serves the rest of the gateway too. `classified_text` skips `STRUCTURAL_KEYS` and a `data` that is inline binary (beside `"type": "base64"` or `format`), so an Anthropic text document is read; it collects the strings as borrowed fragments and, when they exceed the budget, keeps its first quarter and its last three quarters joined by a newline (each cut on a character boundary), so the latest turn of a long chat is always scored (#3453); with the windows of #3513 the budget is `max_scored_bytes` rather than one window. `SemanticGuardsConfig::model_root` (#3454) is `skip_serializing`, so it is read from a file and never leaves the process in `/internal/snapshot` (no format change); `rolter_gateway::run` resolves it once before the state is built — `--semantic-model-root`, else `ROLTER_SEMANTIC_MODEL_ROOT`, else the file's key (`apply_model_root` over `effective_model_root`, logged with its source, or logged as unconfined when no source sets one; a value that is not UTF-8 refuses startup) — and writes the winner back into the bootstrap config, so `configure` stores it once and `preload`, `apply` and the retry use it unchanged (#3511). `bootstrap_config` refuses to start when `--config` or `ROLTER_CONFIG` names a missing file (a blank one counts as unset); only the default `rolter.toml` may be missing, and `just gateway` creates it from the example first. Every read goes through `confine` and then `open_checked`: `confine` canonicalises the root (`ModelError::Root` if it does not resolve) and the path (a relative one against the process's working directory) and refuses a canonical path outside the canonical root (`OutsideRoot`); `open_checked` opens that path exactly once with `O_NONBLOCK` (and, under a root, `O_NOFOLLOW`, an `ELOOP` reading as "became a symlink"), then checks the handle, never the path: `fstat` must say regular file, so a FIFO or device swapped in is refused without blocking a blocking-pool thread and the reload awaiting it; under a root, `/proc/self/fd/N` must read back as the canonical path (device and inode compared off Linux), so a directory swapped for a symlink after `confine` is caught too. The bytes are read through that handle into a buffer sized from its `fstat`. A hard link into the root to a file elsewhere is not detected; the pin covers whatever is read. The control plane validates the shape only (`validate_local_fields` in `guardrails.rs`, which also holds `max_retries` to 0, as migration 0190's check does); it never opens the path, and the provider trial stays webhook-only. An `Unknown` kind is named by `GatewayConfig::fail_closed_unknown_values`, skips the url and model checks of `validate`, and is listed through `known_values!` so a config file's typo is refused with the accepted values.

Successful reads are retained by digest before their channel handoff (#3578).
A timed-out receive and the receiver's drop are separate events: a buffered
send between them can succeed even though the batch will never take its result.
Keeping the model before sending preserves it for the retry in that case too;
a batch that accepts its answer removes the retained copy. The regression
`a_successful_read_after_timeout_survives_receiver_drop` exercises the real
fixture reader at that boundary and checks that repeated retries read the file
only once. Normal accepted reads leave no retained entry.

### The `onnx/1` format (#3443)

`Model` (`local_classifier.rs`) is what the registry holds: `Linear(LinearModel)` always, and `Onnx(local_onnx::OnnxModel)` only under the `onnx` cargo feature (off by default; `rolter/onnx` forwards it). The `semantic_onnx` stability marker covers the manifest and native runtime compatibility contract. This is source-build only; the published image does not enable it. The binding is pinned to the release candidate `ort = 2.0.0-rc.15`. Without the feature an ONNX manifest produces `ModelError::Unsupported`, and the provider follows its failure mode.

`local_onnx.rs` validates the manifest before opening its parts, checks library availability before expensive reads, then reads the tokenizer (≤ 64 MiB) and serialized graph (≤ 1 GiB) through `read_pinned`. The model takes `input_ids` and optionally `attention_mask` and `token_type_ids`, fed as `i64` `[1, n]` tensors. An empty-input inference must succeed before the model is registered, including extracting f32 output with exactly one value per label. A compatible graph can accept a zero-id `[1, 0]` input. Scores use `softmax` or `sigmoid`, with NaN treated as 1.

The already byte-bounded text is tokenized into overlapping `max_tokens` windows; special tokens are reapplied to each window, and category maxima are folded across them. Native scoring does not nest token windows inside the linear classifier's byte windows. At most 64 native windows are scored. A larger token stream keeps the first quarter and last three quarters of that window budget, flags truncation, and obeys `on_truncated` even when the bytes themselves fit the provider budget.

**External-data caveat:** the pins and `model_root` cover the manifest, tokenizer and serialized graph only. ONNX Runtime can resolve external-data initializers of an in-memory graph relative to the process working directory; those sidecars bypass `read_pinned`, its digests and its confinement. Deploy trusted, self-contained graphs with tensor data embedded in the `.onnx` file, not external-weight exports. The gateway does not validate or confine those external references.

ONNX Runtime uses `load-dynamic` and the CPU-only `api-21` path: automatic device selection under `api-22` crashed with the tested runtime 1.22.0. The ONNX library itself is neither linked nor downloaded at build time. `library()` checks availability without consuming the binding's single environment creation; failed loads remain retryable. `RuntimeOwner` anchors a successful environment to the classifier manager across empty reloads, models keep it alive until their sessions drop, and detached readers retain only a weak owner. No static strong environment is left for C++ process teardown.

Each single-threaded session has a per-model admission semaphore acquired before the gateway-wide `local_concurrency` permit, so its waiters do not starve linear providers. Both waits share the provider's deadline. A blocking inference retains both permits until it actually finishes, even if its async caller times out; a running native call is not preempted.

The tokenizer keeps the pure-Rust fancy-regex backend. An adversarial custom Split reproduced its iterator silently stopping at a backtrack limit and hiding a late injection. Serialized `Regex` patterns are therefore validated against the bounded, linear Rust regex engine at model load: lookaround, backreferences and oversized patterns are refused permanently, including patterns nested in normalizer or pre-tokenizer sequences. Built-in pre-tokenizers such as ByteLevel remain supported and are covered by real RoBERTa/onig parity vectors. A regular Split still preserves the late needle on repeated calls. This avoids adding the archived oniguruma C runtime merely to turn its retry-limit panic into a failure. Unexpected tokenizer panics are caught as provider failures under Rust's default unwinding strategy.

## Streams (ADR-0037)

In `RequestCtx::admit_semantic_leg`, right after the built-in output rules' stream check (`RequestCtx::output_guard`): a streamed request whose policy runs `post_call` providers is refused with `400 guardrail_streaming_unsupported` under `streaming = "reject"` (before the upstream call). Under `"buffer"`, `stream_response` reads the upstream body with `read_bounded` (16 MiB, `MAX_BUFFERED_STREAM_BYTES`; over the cap is withheld), translates it as a whole SSE body, shows the providers `stream_content` and then hands it to `buffered_response(.., is_sse = true)` or `withheld_response`. The `SemanticLeg`'s `stream` flag is reset to what actually came back, so a JSON answer to a streamed request is judged as JSON.

## Audio transcriptions (#3331)

`proxy_multipart` serves `/v1/audio/transcriptions` and `/v1/audio/translations`. The request is audio, so no request-stage subsystem runs on it; the response is small text, so it builds the same response stage as `proxy` — the `OutputGuard`, a `SemanticLeg` for a policy that `runs_at(PostCall)`, the `post_response` plugins and a `PiiResponseLeg` with no ticket — and passes them to `stream_response` in a `DeliveryPolicy` with `transcript = true`. `DeliveryPolicy::apply` then shows every leg a `text`, `srt` or `vtt` answer as `{"text": …}` and unwraps the delivered body again (`transcript_text`); a successful body that is not a JSON object and not UTF-8 is withheld as `unreadable_transcript`, so a covering policy never lets a transcript through unjudged. `apply_output` scans `text` and `segments[].text` on the two paths, and once anything was redacted removes `words` and `logprobs`, whose one-token entries no rule can match a multi-token value in. A `stream=true` transcription (#3432) gets what a streamed chat request gets: `proxy_multipart` reads the `stream` form field and, before dialling, refuses it through the helpers the chat path shares (`output_rules_stream_refusal` under `streaming_post_call = "reject"`, `SemanticLeg::rejects_stream` / `policy_stream_refusal`, `plugin_stream_refusal` for a fail-closed plugin, `pii_stream_refusal`), and otherwise builds every leg as for a non-streamed request: the legs a stream skips are set aside only after the upstream answers, and only when it answered with an event stream, so a model that ignores `stream` (whisper-1) is judged as before and the field cannot switch a leg off. The form fields are read in one pass (`multipart::text_fields`). `is_sse` comes from the upstream `content-type`; under `streaming = "buffer"` `stream_response` buffers the stream, `stream_text` joins the `transcript.text.delta` events (or takes the `transcript.text.done` event's whole text) for the providers, and the stream is replayed. The plain-text transcript wrapping is skipped for an SSE body. An event stream the request did not announce, on a route with a whole-body leg (built-in output rules, plugins, the sanitizer), is withheld by `withhold_unrequested_stream` as `unrequested_stream`, read up to the 16 MiB cap for its usage (#3471). `stream_text` judges the joined deltas, and adds the `transcript.text.done` and `transcript.text.segment` text where it differs from them. The audio units are read from the upstream body before the policy runs (`RequestLog::billed_units`), so a withheld or rewritten transcript is billed by the duration the provider stated. The decision against refusing these requests, as a realtime session is refused, is that nothing here prevents buffering.

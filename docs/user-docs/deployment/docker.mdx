The bundled Compose file runs the gateway, the control plane and all three backing stores. It comes in two shapes, and the one you start decides who can reach your data.

|                  | Local stack                                                                                                                               | Team stack                                                                         |
| ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| For              | One person, on a machine nobody else can reach                                                                                            | A team sharing one host                                                            |
| Start it with    | `docker/docker-compose.yml`                                                                                                               | The same file plus `docker/docker-compose.team.yml` and an env file                |
| Management plane | Open. There is no admin token, so everyone who reaches port 4001 is a superadmin                                                          | Closed behind `ROLTER_ADMIN_TOKEN`, published on `127.0.0.1`                       |
| Datastores       | Published on every interface. Postgres has the example `rolter`/`rolter` login, Redis has no password, ClickHouse has a passwordless user | Each has a password from the env file. Only Postgres is published, on `127.0.0.1`  |
| Secrets          | None                                                                                                                                      | KEK, admin and internal tokens, key and session peppers, three datastore passwords |
| Gateway          | Follows the control plane                                                                                                                 | Follows the control plane, with the internal token and the key pepper              |

<Warning>
  The local stack is open on purpose. Do not start it on a shared host, a server or a cloud VM. Adding `ROLTER_ADMIN_TOKEN` to it by hand closes the management API only: Postgres, Redis and ClickHouse stay reachable from the network, so anyone there can write an account into Postgres, reset budget counters in Redis or read every request log from ClickHouse around the control plane. Use the team stack.
</Warning>

Both shapes build the image from your checkout on the first start, which takes several minutes. The build turns on the `postgres` feature. Without it the control plane ignores the database URL, keeps everything in memory and has no sign-in and none of the dashboard's create, edit and delete screens. The published `ghcr.io/rolter-ai/rolter` image is built without that feature ([#2405](https://github.com/rolter-ai/rolter/issues/2405)), so it cannot replace the build here yet.

Both shapes need Docker Compose 2.24 or later.

## Local stack

<Steps>
  <Step title="Start the stack">
    Bring up all five services in the background:

    ```bash
    docker compose -f docker/docker-compose.yml up -d
    ```

    Docker Compose starts PostgreSQL, Redis and ClickHouse first, then the control plane, then the gateway. On first boot the control plane applies the database schema itself, so no manual SQL is required. The gateway polls the control plane for its configuration: a provider, route or virtual key you create in the dashboard reaches it within a few seconds, without a restart.

    <Note>
      ClickHouse asks for 262144 open files. If the ClickHouse container fails to start with `error setting rlimit type 7: operation not permitted`, the container runtime (often rootless Docker or Podman) cannot grant that many. Set a lower limit in `docker/.env` and start again: run `echo CLICKHOUSE_NOFILE=20000 >> docker/.env`, then `docker compose -f docker/docker-compose.yml up -d`. Compose reads `docker/.env` because it sits beside the first `-f` file; a `.env` at the repository root does not set this value.
    </Note>

  </Step>
  <Step title="Give it provider keys (optional)">
    The bundled `rolter.toml` reads `OPENAI_API_KEY` and `ANTHROPIC_API_KEY` from the gateway's environment. Export them before `up`, or put them in `docker/.env`. A `.env` at the repository root is read only if you pass `--env-file .env`.

    To add providers in the dashboard instead, export a key-encryption key before `up`. Without one the dashboard refuses to store a provider key.

    ```bash
    export ROLTER_KEK=$(openssl rand -hex 32)
    ```

    <Note>
      This key seals provider keys in the database. Keep it: a new one strands every key stored under the old one.
    </Note>

  </Step>
  <Step title="Watch the gateway logs">
    Confirm the gateway started cleanly by tailing its logs:

    ```bash
    docker compose -f docker/docker-compose.yml logs -f gateway
    ```

    You should see the gateway announce the port it is listening on and that it applied a config snapshot from the control plane. Press `Ctrl+C` to stop following.

  </Step>
  <Step title="Verify the services are running">
    Once all containers are up, the stack exposes the following default ports:

    | Service | Address | Notes |
    | --- | --- | --- |
    | **Gateway** | `http://localhost:4000` | OpenAI/Anthropic-compatible API |
    | **Control plane \+ UI** | `http://localhost:4001` | Dashboard and config API |
    | **PostgreSQL** | `localhost:5432` | Source of truth for all config |
    | **Redis** | `localhost:6379` | Config pub/sub and hot-reload events |
    | **ClickHouse (HTTP)** | `localhost:8123` | Request logging and analytics |
    | **ClickHouse (native)** | `localhost:9000` | ClickHouse native protocol |

    Open `http://localhost:4001` in your browser to access the dashboard.

  </Step>
  <Step title="Send a test request">
    Confirm the gateway is healthy and accepting traffic:

    ```bash
    # Health check
    curl http://localhost:4000/healthz

    # List available models (uses the default dev virtual key)
    curl http://localhost:4000/v1/models \
      -H "Authorization: Bearer sk-rolter-dev"
    ```

    A `200 OK` from `/healthz` and a JSON model list from `/v1/models` confirm the gateway is fully operational.

  </Step>
</Steps>

## Team stack

The team stack layers `docker/docker-compose.team.yml` over the same file. It closes the management plane, gives every datastore a password and reads every secret from an env file, so a value you forgot stops `docker compose up` with a message instead of starting something half-configured.

<Steps>
  <Step title="Generate the secrets">
    `rolter init` writes the five values the control plane and gateway share (install it with `uv tool install rolter`, see [Installation](/installation)). The three datastore passwords are not part of it yet ([#2413](https://github.com/rolter-ai/rolter/issues/2413)), so append them:

    ```bash
    rolter init --env-only
    cat >> .env <<EOF
    ROLTER_PG_PASSWORD=$(openssl rand -hex 24)
    ROLTER_REDIS_PASSWORD=$(openssl rand -hex 24)
    ROLTER_CLICKHOUSE_PASSWORD=$(openssl rand -hex 24)
    EOF
    ```

    | Variable | What it does |
    | --- | --- |
    | `ROLTER_KEK` | Seals provider keys in the database |
    | `ROLTER_ADMIN_TOKEN` | Closes the management API and turns on role-based access control |
    | `ROLTER_INTERNAL_TOKEN` | What the gateway presents to fetch its configuration |
    | `ROLTER_KEY_PEPPER` | Peppers virtual-key digests. The control plane and the gateway must hold the same value |
    | `ROLTER_SESSION_PEPPER` | Peppers the digests of sign-in sessions, invitations, SCIM tokens and recovery codes |
    | `ROLTER_PG_PASSWORD`, `ROLTER_REDIS_PASSWORD`, `ROLTER_CLICKHOUSE_PASSWORD` | Datastore credentials. They end up inside connection URLs, so use hex |

    `ROLTER_PG_USER` and `ROLTER_CLICKHOUSE_USER` default to `rolter`. `ROLTER_CONTROL_HOST` is the address the control plane is published on, `127.0.0.1` in the file `rolter init` writes.

    Keep `.env` out of version control and somewhere it outlives a restart. A new KEK strands every stored provider key, and a new pepper invalidates the keys or sessions issued under the old one. The datastore passwords are set when a volume is first created, so changing one in `.env` later does not change it inside an existing database.

  </Step>
  <Step title="Check the environment">
    The preflight service runs `rolter check --strict` against the same values the control plane will get, with the binary that will run it:

    ```bash
    docker compose -f docker/docker-compose.yml -f docker/docker-compose.team.yml \
      --env-file .env --profile preflight run --rm preflight
    ```

    It prints `all pre-boot checks passed`. `--env-file` goes before `run`: the subcommand has no such flag. A warning fails the check, for example when `ROLTER_CONTROL_HOST` is `0.0.0.0`, which publishes the management plane on every interface.

  </Step>
  <Step title="Start the stack">
    ```bash
    docker compose -f docker/docker-compose.yml -f docker/docker-compose.team.yml \
      --env-file .env up -d --wait
    ```

    The team stack has its own project name, `rolter-team`, so it never reuses the volumes of a local stack you ran before, which hold the example credentials. Every later command (`logs`, `ps`, `down`) needs the same two `-f` flags and `--env-file`.

  </Step>
  <Step title="Create the first administrator and sign in">
    Postgres is published on `127.0.0.1` for this. `rolter-seed` does not ship in the image yet ([#1897](https://github.com/rolter-ai/rolter/issues/1897)), so run it from a checkout of the repository on the same host:

    ```bash
    ROLTER_DATABASE_URL="postgres://rolter:<ROLTER_PG_PASSWORD>@127.0.0.1:5432/rolter" \
      cargo run -p rolter-control --features postgres --bin rolter-seed -- \
      --admin-email you@example.com --admin-password '<a long password>'
    ```

    Open `http://127.0.0.1:4001` and sign in. The provider keys you add in the dashboard are sealed under `ROLTER_KEK`, and the gateway picks up providers, routes and virtual keys within seconds.

  </Step>
  <Step title="Put TLS in front of it">
    The gateway is published on every interface at port 4000, and it authenticates every request with a virtual key. The control plane is published on `127.0.0.1` only. For people who are not on this host, run a reverse proxy that terminates TLS and forward it to port 4001 for the dashboard and to port 4000 for the API. `/internal/*`, which carries decrypted provider keys, is on a separate port, 4002, that is not published, so a proxy cannot forward it.
  </Step>
</Steps>

What the team stack publishes:

| Service                      | Address          | Notes                                                                                                  |
| ---------------------------- | ---------------- | ------------------------------------------------------------------------------------------------------ |
| **Gateway**                  | `0.0.0.0:4000`   | OpenAI/Anthropic-compatible API, virtual keys required                                                 |
| **Control plane \+ UI**      | `127.0.0.1:4001` | Dashboard and management API, admin token or sign-in required                                          |
| **PostgreSQL**               | `127.0.0.1:5432` | Set `ROLTER_PG_HOST_PORT` to move it                                                                   |
| **Redis** and **ClickHouse** | not published    | Reach them with `docker compose ... exec redis redis-cli ping` and `exec clickhouse clickhouse-client` |

The team stack does not read the `rolter.toml` that `rolter init` writes. It mounts `docker/rolter.team.toml`, which defines no providers, routes or virtual keys, in its place: the image's bundled example would otherwise reach the gateway through the control plane with the public `sk-rolter-dev` key in it. Everything is created in the dashboard. To keep some providers in a file, mount your own over `docker/rolter.team.toml` and leave `[[virtual_keys]]` out of it.

<Warning>
  The control plane and the gateway print their Redis and ClickHouse URLs at startup, passwords included ([#2406](https://github.com/rolter-ai/rolter/issues/2406)). Until that is fixed, treat the container logs like the env file.
</Warning>

## Run the single image

The published image runs `rolter easy-up` by default: the gateway, the control plane and the dashboard in one container, answering on the built-in `fake-llm` model with no config file and no database. Release images are signed and carry an SBOM; [Verify images](/deployment/verify-images) shows how to check one before you run it.

```bash
docker run --rm -p 127.0.0.1:4000:4000 -p 127.0.0.1:4001:4001 \
  -e ROLTER_ALLOW_OPEN_MODE=1 \
  ghcr.io/rolter-ai/rolter:latest
```

The image's default command runs `rolter easy-up --host 0.0.0.0`. Inside a container that is required: a published port forwards to the container's network interface, never to its loopback, so a loopback bind answers nothing from the host.

Binding every interface with no `ROLTER_ADMIN_TOKEN` would serve the management API to anyone who can reach it, so the container refuses to start in that state until it is acknowledged:

| You pass                      | What happens                                                                                                                   |
| ----------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| nothing                       | Refuses to start and says why.                                                                                                 |
| `-e ROLTER_ALLOW_OPEN_MODE=1` | Starts with an unauthenticated control plane and a warning banner. Keep the ports on loopback with `-p 127.0.0.1:…`, as above. |
| `-e ROLTER_ADMIN_TOKEN`       | Starts with the management API closed behind the token. Use this for anything other hosts can reach.                           |

Generate the token on its own line and keep it, because the dashboard and the management API ask for it. Then pass it through by name:

```bash
export ROLTER_ADMIN_TOKEN=$(openssl rand -hex 32)
echo "$ROLTER_ADMIN_TOKEN"
docker run --rm -p 4000:4000 -p 4001:4001 \
  -e ROLTER_ADMIN_TOKEN \
  -v "$PWD/rolter.toml:/app/rolter.toml" \
  ghcr.io/rolter-ai/rolter:latest
```

<Warning>
  The admin token closes the management API only. The gateway on port 4000 accepts the virtual keys in `rolter.toml`, and the one the image ships, `sk-rolter-dev`, is printed in these docs and allows every model. Before other hosts can reach port 4000, replace it in the `[[virtual_keys]]` section of your own `rolter.toml` with a key nobody else knows, and mount that file as above. Deleting the section instead leaves the gateway open to anyone.

Once an admin token is set, the control plane also stops handing `sk-rolter-dev` to gateways that poll its snapshot, and reports the omission under `GET /api/v1/config/problems`. A gateway that loads its own `rolter.toml` directly is not covered by that, so the file is still the place to remove it.

</Warning>

Where `sk-rolter-dev` can come from, and how each production path avoids it:

| Path                               | Where the key comes from                                       | What avoids it                                                                        |
| ---------------------------------- | -------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| Single image, no mounted config    | the example baked in as `/app/rolter.toml`                     | mount your own `rolter.toml` without `[[virtual_keys]]`, or run open on loopback only |
| Team compose stack                 | none: it mounts `docker/rolter.team.toml`                      | nothing to do                                                                         |
| Helm chart                         | none: control plane, gateways and preflight read `config.file` | keep `[[virtual_keys]]` out of `config.file` or your `existingConfigMap`              |
| `rolter init --profile production` | none: the generated `rolter.toml` has no `[[virtual_keys]]`    | create keys in the dashboard or API                                                   |
| `rolter init --profile local`      | the example, on purpose                                        | do not ship it                                                                        |

`rolter check` fails with an error on any config file that still declares `sk-rolter-dev`.

## Run just the gateway

If you want to run only the gateway, without the control plane or any backing stores, override the command and mount a `rolter.toml`. This is useful for quick tests or for edge deployments where you manage external databases separately.

```bash
docker run --rm -p 4000:4000 \
  -e OPENAI_API_KEY=$OPENAI_API_KEY \
  -v "$PWD/rolter.toml:/app/rolter.toml" \
  ghcr.io/rolter-ai/rolter:latest rolter-gateway --config /app/rolter.toml
```

Mount your local `rolter.toml` into the container at `/app/rolter.toml`. The gateway reads provider credentials from the environment variables you inject, keeping secrets out of the config file. It binds the `[server] host` from that file, and its clients authenticate with the virtual keys in it: replace the example's `sk-rolter-dev` before the port is reachable from other hosts.

To run the control plane instead of the gateway, override the command with `rolter-control`. It binds loopback unless `ROLTER_CONTROL_HOST` says otherwise, and it follows the same rule as the single image, so give it an admin token along with the bind:

```bash
docker run --rm -p 4001:4001 \
  -e ROLTER_CONTROL_HOST=0.0.0.0 \
  -e ROLTER_ADMIN_TOKEN \
  ghcr.io/rolter-ai/rolter:latest rolter-control
```

## Build the image locally

Both binaries and the compiled dashboard UI are packaged into a single slim Debian image. To build it from source:

The build includes the control plane's database support, sign-in and CRUD API (`CARGO_FEATURES=postgres`, the Dockerfile default), the same as the published image. Pass `--build-arg CARGO_FEATURES=` to build an in-memory-only control plane without them.

<CodeGroup>

```bash Build
docker build -f docker/Dockerfile -t rolter:dev .
```

```bash Run (single image)
docker run --rm -p 127.0.0.1:4000:4000 -p 127.0.0.1:4001:4001 \
  -e ROLTER_ALLOW_OPEN_MODE=1 \
  rolter:dev
```

</CodeGroup>

## Database schemas

Schema migrations are applied automatically on first container start — no manual SQL or migration commands needed.

The PostgreSQL schema is applied by rolter itself: both the control plane and
the seed tool run the migration set on startup and record what they applied.
ClickHouse is initialised by the Compose setup before the application
containers start.

Subsequent starts skip already-applied migrations, so it is safe to bring the stack up and down repeatedly.

<Note>
Do not mount `crates/rolter-store/migrations` into the Postgres container's
`docker-entrypoint-initdb.d`. PostgreSQL would run those files itself on first
init, outside rolter's migration runner, so rolter would see an untracked
database and try to reapply every migration to it — failing on the first
statement that cannot run twice.
</Note>

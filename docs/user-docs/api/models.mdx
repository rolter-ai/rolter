The `/v1/models` endpoint returns the public model names that are configured in your `rolter.toml` and accessible to the authenticated virtual key. You can use this endpoint to discover which model names to pass in the `model` field of chat, completion, or messages requests.

## What is returned

The response lists every model name this gateway accepts in a `model` field, in three forms:

| Id                   | `owned_by`          | What it is                                                                                                                                                                                                            |
| -------------------- | ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `gpt-4o`             | `rolter`            | a **route name** from your configuration. A route configured with `model = "gpt-4o"` that targets the upstream model `gpt-4o-2024-11-20` appears as `gpt-4o` — the upstream id stays an internal concern of the route |
| `openai-edge/gpt-4o` | the provider's name | a **provider-pinned address**: this provider, this upstream model, no cross-provider fan-out                                                                                                                          |
| `edge-fleet/gpt-4o`  | the group's name    | a **provider-group address**, balanced across the group's members                                                                                                                                                     |

When virtual keys are configured, the list is filtered to the models that the authenticated key's `models` allow-list permits. A key configured with `models = []` (empty) can see all of them.

### How the provider-pinned list is built

A provider-pinned address works for any model the provider actually serves, not only the ones your routes mention. To list them, Rolter reads the model catalogue each provider returns to its **health probe** and caches it.

<Note>
  The wider list requires active health checks (`[health] enabled = true`). With probing off, the provider-pinned entries are derived from your route targets alone, so a provider that serves more models than your routes name will under-report them. This changes only what is *listed*: `provider-slug/model` routes either way, so an address you know works even when it is not in the list.
</Note>

At most 200 catalogued models are listed per provider, so one aggregator with a
several-hundred-model catalogue cannot bury the rest of your fleet. Models named
by a route target are always listed, regardless of that cap.

<Note>
  Rolter also exposes a built-in `fake-llm` model that responds locally without forwarding to any upstream. It appears in the model list unless a configured route shadows it with the same name. It is useful for testing authentication and connectivity without incurring upstream costs.
</Note>

## Request

**`GET /v1/models`**

### Headers

<ParamField header="Authorization" type="string">
  `Bearer <virtual-key>` — your Rolter virtual key. Required when virtual keys are configured. Omit only when the gateway is running open (no keys configured).
</ParamField>

## Example

<CodeGroup>

```bash curl
curl http://localhost:4000/v1/models \
  -H "Authorization: Bearer sk-rolter-dev"
```

```python OpenAI SDK
from openai import OpenAI

client = OpenAI(
    base_url="http://localhost:4000/v1",
    api_key="sk-rolter-dev",
)

models = client.models.list()
for model in models:
    print(model.id)
```

</CodeGroup>

## Response

```json
{
  "object": "list",
  "data": [
    {
      "id": "gpt-4o",
      "object": "model",
      "owned_by": "rolter"
    },
    {
      "id": "claude",
      "object": "model",
      "owned_by": "rolter"
    },
    {
      "id": "llama",
      "object": "model",
      "owned_by": "rolter"
    },
    {
      "id": "openai-edge/gpt-4o",
      "object": "model",
      "owned_by": "openai-edge"
    },
    {
      "id": "openai-edge/o3-mini",
      "object": "model",
      "owned_by": "openai-edge"
    }
  ]
}
```

<ResponseField name="object" type="string">
  Always `"list"`.
</ResponseField>

<ResponseField name="data" type="array">
  Array of model objects, one per accessible model name.

  <Expandable title="Model object fields">
    <ResponseField name="id" type="string">
      The name you pass as `model` in request bodies: a route name (e.g. `"gpt-4o"`), a provider-pinned address (`"openai-edge/gpt-4o"`), or a provider-group address (`"edge-fleet/gpt-4o"`).
    </ResponseField>

    <ResponseField name="object" type="string">
      Always `"model"`.
    </ResponseField>

    <ResponseField name="owned_by" type="string">
      `"rolter"` for a route name, otherwise the name of the provider or provider group the address pins — so a client can group the list by where each model comes from.
    </ResponseField>

  </Expandable>
</ResponseField>

## Virtual key filtering

If your key is scoped to a subset of models, only those appear in the response. For example, a key configured as:

```toml
[[virtual_keys]]
key = "sk-gpt-only"
models = ["gpt-4o"]
```

returns only the `gpt-4o` entry, even if `claude` and `llama` routes are defined. Requesting a model outside the key's allow-list on an inference endpoint returns `403 Forbidden`.

<Tip>
  Use this endpoint from your application at startup to validate that the expected model routes are reachable with the configured key before serving user traffic.
</Tip>

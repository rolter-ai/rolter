"OpenAI-compatible" and "SCIM 2.0" are claims, and a claim is only useful when you
can check it. This page lists every external specification Rolter implements,
translates, emits, parses or forwards, and every provider kind it can reach,
with:

- the **official source** and the **revision** reviewed — a dated version, a
  release, an RFC, or for a living document the date it was last read;
- the **conformance level**: how much of the specification Rolter actually
  honours;
- what is **supported**, what is **omitted**, and where Rolter **deviates** on
  purpose;
- the **tests** that demonstrate the claim.

The tables below are generated from the registry
[`crates/rolter-core/specifications.toml`](https://github.com/rolter-ai/rolter/blob/master/crates/rolter-core/specifications.toml),
the one place a reviewed version or URL is written down. The same data is in the
gateway's and the control plane's `GET /openapi.json`: each operation a
specification governs carries a standard `externalDocs` link plus three
extensions, `x-rolter-spec-refs` (the registry ids), `x-rolter-conformance` and
`x-rolter-reviewed-at`. Rolter never adds a field to a vendor's request or
response payload.

## Conformance levels

| Level                | Meaning                                                                                                                               |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| `native-passthrough` | The vendor's wire format, forwarded or served unchanged. Rolter reads the fields it needs (`model`, `stream`, `usage`).               |
| `translation-subset` | Rolter rewrites between dialects. Only what the record lists is translated; a part with no equivalent fails the request.              |
| `transport-only`     | Bytes are relayed. Rolter neither validates the payload nor negotiates a version, so the two ends must agree between them.            |
| `extension`          | The vendor's shape plus Rolter's own additions.                                                                                       |
| `partial`            | Some of the specification, as listed.                                                                                                 |
| `provider-profile`   | A provider's base URL, credential header and path over an OpenAI-shaped transport. Proves the profile, not full compatibility.        |
| `unverified`         | A provider kind with no located public API reference. Whether it speaks an OpenAI-compatible API at a stable base is not established. |

## Versions

- **OpenAI** is recorded as REST `v1`. That API evolves by backward-compatible
  additions and gives its type system no finer version, so Rolter records a
  review date rather than inventing one. Rolter does not consume OpenAI's
  published OpenAPI artifact, so no commit of it is pinned.
- **Anthropic** is recorded with its dated `anthropic-version`. A request that
  states none is sent with `[compatibility] anthropic_version`, which is the
  recorded version when no value is stored or configured; a client's own `anthropic-version` always wins. The
  health probes and the provider connection test send the recorded version,
  not your `[compatibility]` pin: a probe asks whether the API answers and
  accepts the key, which no dated version changes. See
  [Compatibility](/configuration/compatibility).
- **MCP** is `partial`: the gateway applies your organization's tool groups to
  every JSON-RPC call and answers an upstream `insufficient_scope` with a
  step-up challenge, but it relays `MCP-Protocol-Version` without negotiating
  it, so the recorded version is `forwarded`. The MCP OAuth client is recorded
  against the dated revision that carries every requirement it implements.
- **OpenTelemetry GenAI** attributes are pinned to the semantic-conventions
  release they were audited against, and the rolter-local values are listed as
  deviations. OTLP is recorded by its protocol version, separately from the SDK
  crates that implement it.

#### OpenAI Chat Completions

`openai-chat-completions` · OpenAI · [primary source](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create)

- **Supported:** request and response bodies are forwarded unchanged to an OpenAI-shaped upstream; the gateway reads `model`, `stream`, `messages` and `usage`
- **Supported:** `chat.completion.chunk` SSE frames, forwarded incrementally
- **Supported:** translation to Anthropic Messages and Gemini (see the translation records)
- **Omitted:** no request validation beyond `model`: unknown fields reach the upstream, which judges them
- **Omitted:** the served OpenAPI schema names only the fields rolter reads, not the full vendor type
- **Deviations:** a `provider-slug/model` name pins a provider and is rewritten to the upstream model before forwarding
- **Deviations:** guardrails, plugins and the PII sanitizer a route configures may refuse or rewrite a request or response; with none configured the bodies pass unchanged
- **Evidence:** `crates/rolter-gateway/tests/integration.rs::non_streaming_request_proxies_upstream_body`<br />`crates/rolter-gateway/tests/integration.rs::streaming_request_passes_through_sse`<br />`crates/rolter-gateway/tests/integration.rs::output_guardrail_masks_a_non_streaming_completion`<br />`crates/rolter-gateway/tests/integration.rs::pre_upstream_plugin_transforms_the_request_body`

#### OpenAI Responses and its lifecycle methods

`openai-responses` · OpenAI · [primary source](https://developers.openai.com/api/reference/resources/responses)

- **Supported:** create: native passthrough to an OpenAI upstream, streaming included
- **Supported:** create: translated to Chat Completions, Anthropic Messages or Gemini when the route's target speaks one of those

A program that manages rolter through the control-plane API, such as a CI job that rotates a project key, a GitOps pipeline that applies routes or a script that creates a project per customer, used to choose between two credentials: the **admin token**, which is superadmin over the whole deployment and shared by everything that holds it, or a **person's session**, which belongs to a browser and expires. An **API token** is a third one: a named service account that holds **one role at one organization, team or project**.

The control plane resolves the token to that role, so every permission check works exactly as it does for a person holding it. A token with the `member` role on one project can do what a project member can do there and nothing else.

## What a token can and cannot do

- It holds one built-in role (`admin`, `member`, `viewer`) or one [custom role](/security/rbac#custom-roles-and-access-profiles) of the organization, at the scope it was minted for. It reaches that scope and everything below it, never a sibling or the level above.
- It **never** reaches deployment-wide settings (feature flags, the security settings, cluster nodes, alerting, the configuration export) and never holds a [deployment role](/security/rbac#deployment-roles). Those stay with the admin token, superadmins and the deployment roles.
- It **cannot manage tokens**: minting, listing, rotating and revoking answer `403` for a token, so a leaked one cannot mint a successor that outlives its own revocation.
- It cannot read request logs or analytics, which are scoped to people, and it is not a session: the dashboard's account endpoints answer `401`.
- An `admin` token can do what an admin of its scope can do, including granting memberships there. Give automation the narrowest role that does the job.

It is not a virtual key (the data plane, `/v1/*`) and not a SCIM token (provisioning, `/scim/v2/*`); each is refused at the other's door. See [which key do I need](/security/which-key).

## Mint a token

Minting takes an **admin of the token's own scope**: an org admin mints org-wide, team and project tokens, and a project admin mints tokens for that project only. A token therefore never holds more than the person who made it.

```bash
curl -s -X POST https://control.example.com/api/v1/orgs/$ORG_ID/api-tokens \
  -H "Authorization: Bearer $ROLTER_SESSION_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"name": "ci-deploy", "project_id": "'$PROJECT_ID'", "role": "member", "expires_in_days": 30}'
```

| Field             | Meaning                                                                                           |
| ----------------- | ------------------------------------------------------------------------------------------------- |
| `name`            | required, at most 80 characters; it is what the audit log shows                                   |
| `team_id`         | scope the token to a team; omit both ids for an org-wide token                                    |
| `project_id`      | scope the token to a project (its team, if named, must match)                                     |
| `role`            | `admin`, `member` or `viewer`                                                                     |
| `custom_role_id`  | an org-defined role of this organization instead; give exactly one of `role` and `custom_role_id` |
| `expires_in_days` | `1` to `730`; **90** when omitted                                                                 |
| `never_expires`   | `true` opts out of the expiry; it cannot be combined with `expires_in_days`                       |

The response is the token row plus `secret`, a `rolter_api_…` value. **The secret is shown once.** Rolter stores only a peppered SHA-256 digest of it, the same way it stores sessions and virtual keys, so a lost secret is rotated, not looked up.

Use it like any control-plane credential:

```bash
curl -s https://control.example.com/api/v1/routes \
  -H "Authorization: Bearer rolter_api_…"
```

## List, rotate and revoke

| Request                                | Does                                                                                                                                                |
| -------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /api/v1/orgs/{org_id}/api-tokens` | lists the organization's tokens, revoked and expired ones included, with the `token_prefix`, scope, role, expiry and `last_used_at`; never a secret |
| `POST /api/v1/api-tokens/{id}/rotate`  | returns a new `secret`; the old one stops working in the same instant. A revoked or expired token answers `409` `api_token_inactive`                |
| `DELETE /api/v1/api-tokens/{id}`       | revokes the token; it stops resolving on its next request                                                                                           |

An org admin lists every token of the organization; a team or project admin lists the tokens of the scopes they administer. A token also stops working when it expires, when its organization, team or project is deleted, or when its custom role is deleted.

A token outlives the person who minted it, so revoke the tokens of anyone who leaves: `created_by` names the minter.

## Audit

Minting, rotating and revoking write `api_token.create`, `api_token.rotate` and `api_token.revoke` to the organization's audit log, naming the token and its scope but never the secret. Everything else a token does that is audited has **no actor account** and carries the token's `id` and `name` in `detail.api_token`, so a pipeline's changes are told apart from a person's and from another pipeline's.

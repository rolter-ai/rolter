<Warning>
  **Experimental.** Plugins may change shape or be removed in a minor release.
  The webhook payload Rolter posts to a plugin carries no version of its own, so
  a change to that payload cannot be made compatibly — an endpoint written
  against today's fields may need editing when it moves. The stored
  configuration (slug, scope, order, failure policy, endpoint) is the settled
  part; the request body is not.
</Warning>

Open **Plugins** to arrange desired request and response middleware across three stages:

- **Pre-route** — before Rolter selects a route.
- **Pre-upstream** — after routing and immediately before provider delivery.
- **Post-response** — after the provider returns and before client delivery.

Each webhook configuration has a stable slug, an organization or project scope, an order, a failure policy, an HTTP endpoint, an optional secret environment-variable reference, and a JSON object with plugin-specific settings.

An **enabled** row is live: the gateway consults it on every matching request at its configured stage, in `position` order alongside every other enabled plugin at that stage for the same organization/project.

## Scope

An instance with no `project_id` applies to every project in its organization. A project-scoped instance applies only to that project. If both an org-level and a project-level instance are enabled at the same stage, both run, interleaved by `position` — the org tier does not always run first or last.

## Dispatch

At each stage the gateway sends the request or response body under inspection to the plugin's `endpoint` as JSON, and the plugin replies with a decision:

- `allow` — forward unchanged
- `transform` — replace the content with the plugin's response before continuing to the next plugin (or upstream/the client)
- `block` — reject the request with an OpenAI-compatible error, ending the chain
- `annotate` — forward unchanged, annotations are recorded but not applied

`post_response` only inspects non-streaming responses; a streamed response is delivered without running the `post_response` chain, since masking it would require buffering the whole stream (the same constraint the built-in output guardrails have).

## Failure policy

- **Fail open** favors availability: an unreachable, timed-out, or erroring plugin is treated as `allow`.
- **Fail closed** favors enforcement: the same failure blocks the request with an OpenAI-compatible error.

A `block` from any plugin in the chain stops it immediately — later plugins in the same stage never run.

## Secrets

`secret_env` contains only an environment variable name such as `ROLTER_PLUGIN_TOKEN`. Put the value in the gateway environment. The control-plane API never accepts or returns the secret itself.

## API

| Method | Endpoint | Purpose |
| --- | --- | --- |
| `GET`, `POST` | `/api/v1/orgs/{org_id}/plugins` | List or install configurations |
| `PUT`, `DELETE` | `/api/v1/plugins/{id}` | Update or remove a configuration |

Reads require viewer access at the organization. Mutations require admin access at the configuration's organization or project scope, and every mutation is written to the audit log.

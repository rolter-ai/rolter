A provider is one upstream endpoint plus the credential Rolter uses to reach it. That credential is the *provider key* — the one the provider issued to Rolter, never the virtual key a client sends ([which key do I need?](/security/which-key)). Routes and provider groups select *targets*, and every target names a provider.

Add them from **Providers** in the dashboard, or through the management API.

---

## Where the credential lives

There are two places, and they resolve in this order:

1. **A stored key** — typed into the dashboard, sealed with AES-256-GCM under `ROLTER_KEK` before it reaches the database, and never returned by the API again.
2. **An environment variable** — `api_key_env` names a variable the process reads at snapshot time. The value never enters the database at all.

A stored key wins when both are set.

<Warning>
Storing a key requires `ROLTER_KEK` on the control plane, and the gateway needs the **same** value to decrypt what arrives in a snapshot. With it unset, the control plane still starts and the provider row still saves — the key simply cannot be sealed or read back. Run `rolter check` before boot; it fails on exactly this.
</Warning>

## Test connection

Configuring a provider is otherwise a write with no feedback. The row saves whether or not the base URL is right, and the first sign of a problem is a failed request through the gateway, attributed to whichever route happened to select it.

**Test connection** on a saved provider closes that loop:

```bash
curl -X POST https://control.example.com/api/v1/providers/$ID/test
```

```json
{
  "reachable": true,
  "probed_url": "https://api.openai.com/v1/models",
  "status": 200,
  "latency_ms": 142,
  "credential": "stored",
  "models_found": 38,
  "error": null
}
```

It issues a `GET` against the provider kind's free model-list endpoint — the same one the gateway's health sweep uses, so a green test means the sweep will agree. It is a catalogue call, not a completion, so it costs nothing to run.

### Reading the result

| Field | What it tells you |
|---|---|
| `probed_url` | the URL actually tried. A doubled `/v1` is the most common misconfiguration and is invisible without this |
| `credential` | how the key was resolved — `stored`, `env`, or `none`. Separates "wrong key" from "no key configured" |
| `models_found` | how many models the upstream listed. A provider can be reachable and still serve nothing |
| `status` | absent when the request never completed at all (DNS, TLS, connection refused, timeout) |

A `401` names which credential source was used, so a rejected key points at the right place to fix it.

### When something answers, but not with a model list

`reachable` is not "the upstream returned 2xx". For provider kinds whose probe is a model catalogue, it means the response **was** a catalogue. A catch-all route, an SPA index, a reverse proxy or a login portal will all answer `200` at an arbitrary URL, and reporting those as reachable moves you on to debugging the wrong layer.

That case is reported as its own thing — a 2xx status with `reachable: false`:

```json
{
  "reachable": false,
  "probed_url": "https://gpustack.example.com/v1/v1/models",
  "status": 200,
  "models_found": null,
  "error": "200: https://gpustack.example.com/v1/v1/models answered, but not with a model list. Something other than the provider's API is serving that URL — check api_base for a duplicated path segment, a catch-all route or a login portal."
}
```

The usual cause is a duplicated path segment in `api_base` — see [the `/v1` rule](#where-the-credential-lives) — where the upstream's own catch-all answers `200` at the doubled path.

The dashboard renders this as its own amber state — *Answered, but not with a model list* — rather than the red used for a refused connection or a rejected key. The host is up, and it is the URL or the service behind it that is wrong, which is a different thing to go and fix.

Kinds whose probe is a liveness endpoint rather than a catalogue keep 2xx as the criterion. Hugging Face TEI is probed at `/health`, which has no catalogue to return, so a bare `200` there is the whole verdict and `models_found` stays `null`.

<Note>
The probe reads the **stored** row, not what is currently typed in the form. Save first, then test. The credential is sealed server-side and never leaves the control plane, so a draft key could not be tested without transmitting it somewhere first.
</Note>

### When the credential cannot be read

If the stored key was sealed under a different `ROLTER_KEK` — or the KEK is unset — the test reports that directly and **does not contact the upstream**:

```json
{
  "reachable": false,
  "credential": "stored (KEK unset)",
  "error": "the stored credential for 'openai-primary' could not be read: ROLTER_KEK is unset or does not match the key it was sealed with. The upstream was not contacted."
}
```

This is a deployment problem, not a provider problem, and the message says so rather than reporting the upstream as down.

### What a green result does not prove

The probe is a model-list call. A few self-hosted runtimes serve their catalogue without checking authorization, so on those a wrong key can still return `reachable: true`. The hosted providers all authenticate the endpoint, so the check is meaningful there. Treat `reachable` as "the provider's API answered with its catalogue", and `401` as authoritative when it appears.

## Egress policy

The base URL is checked against the egress policy when the provider is created, and **again** on every test. A stored row is not a standing permission to egress: if the policy has been tightened since, the test fails on the policy rather than reaching the host.

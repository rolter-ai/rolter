Client settings cover the seam between your callers and your providers: what address clients dial, which of their headers survive the hop, and what Rolter attaches on the way out.

Edit them from **Settings → Client Settings** in the dashboard, or through the management API. Changes reach every gateway through the config snapshot, with no restart.

---

## Base URL

The address clients point their SDK at. Set it when the gateway sits behind a load balancer or a custom domain, so the connection snippet in the dashboard matches what a caller can actually reach.

Leave it empty and the dashboard falls back to its own origin. This value is advisory: the gateway never reads it, and setting it does not change what the gateway listens on.

---

## Forwarded request headers

An allowlist of inbound client headers passed through to the upstream provider. Anything not on the list is dropped at the gateway — that is the default, and an empty list means Rolter sends exactly what it sent before this setting existed.

Trace-context headers (`traceparent`, `tracestate`, `b3`) propagate whether or not they are listed, so distributed tracing cannot be broken by editing this list.

Some headers can never be forwarded, because forwarding them would hand a caller the gateway's own credentials or corrupt the upstream request: `authorization`, `x-api-key`, `api-key`, `host`, `content-length`, `content-type`, `transfer-encoding`, `connection` and `cookie`. Listing one is rejected.

### `anthropic-*` headers forward by prefix

Every inbound header beginning with `anthropic-` is forwarded to an Anthropic-dialect upstream **unchanged, without an allowlist entry** — including values Rolter has never seen.

Anthropic extends its protocol through headers: a capability pairs an `anthropic-beta` value with body fields, and the pair travels together. A closed allowlist against a vendor that ships new capabilities *as new header values* means every new beta breaks until someone adds it by name, and it does not fail gracefully — stripping the header while the body passes returns a hard `400` (`Extra inputs are not permitted`), while capabilities such as extended context simply never take effect.

<Note>
  The match requires the separator, so a header merely starting with those letters (`anthropicfoo`) is not in the namespace. These headers are also dropped again for a provider that does not speak the Anthropic dialect, so an OpenAI-shaped upstream never receives them.
</Note>

`anthropic-version` is the one value Rolter resolves rather than copies: the client's wins when it sends one, and the deployment's configured `anthropic_version` is the fallback for requests translated from the OpenAI dialect, where the client stated none. Exactly one value is sent.

## Injected upstream headers

Static name/value pairs Rolter adds to every upstream request — a partner id, a routing tag, a billing dimension your provider expects.

Injected headers are applied *before* trace context, so a trace header of the same name still wins. Values are treated as deployment credential material: they reach the gateway through the snapshot, but they are never written to the audit log. The log records which header **names** changed, not what they were set to.

The same reserved list applies here.

---

## Request ID header

The header carrying the end-to-end request id. Rolter reuses the caller's value when one is present, mints a UUID when it is not, and echoes it on the response so a client can find its own call in the logs.

Default is `x-request-id`. It must be a valid header name and cannot be one of the reserved names.

---

## API

Both endpoints are **superadmin only**, and every update is audited.

```bash
curl -H "Authorization: Bearer $ROLTER_ADMIN_TOKEN" \
  https://control.example.com/api/v1/client-settings

curl -X PUT -H "Authorization: Bearer $ROLTER_ADMIN_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
        "public_base_url": "https://gateway.example.com",
        "forwarded_headers": ["x-tenant-id"],
        "injected_headers": {"x-partner-id": "acme"},
        "request_id_header": "x-request-id"
      }' \
  https://control.example.com/api/v1/client-settings
```

The read response also carries `always_propagated` and `reserved`, so a client does not have to hard-code either list.

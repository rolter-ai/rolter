Rolter can inspect request or response content with built-in detectors, custom regular expressions, and a self-hosted HTTP guardrail service. Open **Guardrails → Rules** or **Guardrails → Providers** in the dashboard. These screens require superadmin access.

## Inspection rules

Rules run by ascending position, after any rules defined in the config file. Each rule uses exactly one source:

- **Built-in detector** — email address, phone number, API token, or payment card.
- **Custom regex** — compiled by Rolter's bounded, linear-time regex engine before the rule is published.

Choose `annotate` to count a match without changing traffic, `block` to reject matching traffic, or `redact` to replace matches. System messages are excluded unless **Inspect system messages** is enabled. A paused rule stays stored and ordered but does not enter gateway snapshots.

A response rule that blocks runs after the provider has generated and billed the answer. The caller gets a `403 guardrail_blocked`, but the request is still billed and counts toward budgets. Its log row is marked `withheld` and names the rule, and the blocked text is never stored. See [Withheld responses](/observability/logs-and-cost#withheld-responses).

A response rule (stage **Before response**) needs the whole answer, so it cannot act on a streamed one. The deployment-wide `streaming_post_call` setting in the `[guardrails]` block of `rolter.toml` decides what happens instead:

- `reject` (the default) — while the rule is enforced, a request with `"stream": true` on a route the rule covers is refused with `400 guardrail_streaming_unsupported`. Chat clients and coding agents usually stream, so one response rule can refuse most interactive traffic.
- `passthrough` — the stream is served and the rule does not see it. Only non-streamed responses are checked.

The rule dialog shows which of the two applies as soon as **Before response** is picked, and each response rule's card repeats it in one line. Both read the value from the effective configuration (`GET /api/v1/config`). When that cannot be read, they say so and describe both outcomes rather than assuming the default. The dashboard shows the setting but does not change it.

The deployment-wide `guardrails` feature flag remains the kill switch. Turning it off pauses every built-in and custom rule, and every config-file rule, without deleting the registry. While it is off, **Guardrails → Rules** shows a banner saying no rule inspects traffic, with a link to **Feature Flags**, and every rule's card says **not enforced** instead of **enforced**.

### What the Rules screen reports

A card's status comes from the policy the control plane hands to gateways, read from the effective configuration (`GET /api/v1/config`), not only from the rule's own switch:

- **enforced** — the rule is in the effective policy and the `guardrails` flag is on.
- **not enforced** — the rule is in the policy, but the flag is off.
- **paused** — the rule is switched off on its card.
- **overridden by config file** — the config file defines a rule with the same name. The file's rule wins a name clash, so this card's rule does not run. The card names the file rule, which is listed below under **Config-file rules**. A paused rule under a file rule's name says it would not run if resumed, and the rule dialog warns when you type a name the config file already uses.
- **status unknown** — the effective configuration could not be read. A banner says so and offers a retry; the screen does not assume the rules are enforced.

Rules defined in the config file are listed under **Config-file rules**, read-only, in the order they run. They run before the rules added on the screen and change only when the file does.

The effective configuration does not say where each rule came from, so the screen infers it from names. A rule the configuration carries is a config-file rule when no card has its name, when the card with its name is paused, or when it differs from that card in any field. A config-file rule identical in every field to an enabled card cannot be told apart from it and is shown as that card. Enforcement is the same either way, but deleting or pausing the card would leave the file's copy running. [#2249](https://github.com/rolter-ai/rolter/issues/2249) tracks reporting the source directly.

## External providers

Register any number of vendor-neutral HTTP services, but activate only one at a time. Activating a provider atomically deactivates the previous provider because each gateway has one external guardrail webhook contract.

Choose the failure policy deliberately:

- **Fail closed** rejects traffic when the provider times out or errors. This favors enforcement.
- **Fail open** lets traffic continue when the provider cannot decide. This favors availability.

The **Evaluation URL** starts empty and is required. The address shown in the empty field is an example, not a default, so a provider cannot be saved pointing at a host nobody typed.

Activating a provider asks for confirmation. The **Activate provider** switch names the provider it would pause, and saving with it on opens a dialog that names that provider again, or says none is active, and states what the failure policy then does to every request: a fail-closed provider refuses a request with `guardrail_blocked` when it times out or errors, and a fail-open one lets it go upstream unchecked. When a config-file webhook is enabled, the dialog also says the new provider is ignored until that webhook is turned off. Cancelling returns to the form with nothing saved. Saving a provider that is already active does not ask again.

The dashboard cannot send a test request to a provider yet, so check that the service answers before you activate a fail-closed provider.

Rolter stores only an environment variable name for bearer or shared-secret authentication. Put the secret value in every gateway's environment; it is never returned by the control-plane API.

Only the **Before upstream** stage (`pre_call`) is enforced today. The gateway does not run the **Before response** stage (`post_call`) yet, so the dashboard does not let you pick it. A provider already saved at that stage is marked **not enforcing** on its card and in the banner. Activating one pauses the active provider and puts nothing in its place.

The banner at the top of **Guardrails → Providers** reports the webhook the control plane hands to gateways, read from the effective configuration (`GET /api/v1/config`), not which registry row is switched on. It is green only when requests go to a guardrail service before they go upstream, and it names that service: a registry provider, or the config-file webhook by its URL. It says so when no webhook is on, and it shows the status as unknown when the effective configuration cannot be read or contradicts the registry.

## Hot reload and config files

Creating, editing, enabling, or deleting a registry entry increments `config_version`, so gateway snapshots update without a restart. Rules defined in the config file remain immutable and win a name collision; dashboard-managed rules extend them. The Rules screen lists the config-file rules and marks a dashboard rule whose name the file takes as overridden. An enabled config-file webhook remains authoritative. The provider registry supplies the webhook when the config-file hook is disabled. While the config-file webhook is on, the Providers screen names it in the banner and marks an active registry provider as overridden.

## API endpoints

| Method          | Endpoint                            | Purpose                     |
| --------------- | ----------------------------------- | --------------------------- |
| `GET`, `POST`   | `/api/v1/guardrails/rules`          | List or create rules        |
| `PUT`, `DELETE` | `/api/v1/guardrails/rules/{id}`     | Update or delete a rule     |
| `GET`, `POST`   | `/api/v1/guardrails/providers`      | List or register providers  |
| `PUT`, `DELETE` | `/api/v1/guardrails/providers/{id}` | Update or delete a provider |

Every mutation is audit logged. Provider bodies accept `auth_kind` as `none`, `bearer`, or `shared_secret`; `auth_env` is required for the latter two and contains only the environment variable name.

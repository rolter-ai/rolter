Request logging is governed by one deployment-wide policy, edited from **Observability → Logs Settings** in the dashboard or through the management API. It decides three things: how much traffic is logged, whether raw payloads are captured alongside the metadata, and how long each is kept.

---

## Sampling

`sample_rate` is the fraction of requests written to the log, from `0` to `1`. The dashboard shows it as a percentage. Lowering it is the first lever to pull on a high-volume deployment — metrics, budgets and rate limits are computed from every request regardless, so sampling only reduces what lands in the log store.

---

## Payload capture

Payload capture stores the raw prompt and completion bodies next to the log metadata. It is **off by default**: payloads contain whatever the caller sent, which is the most sensitive data Rolter touches.

When it is on, four settings narrow what gets stored:

| Setting | Effect |
|---|---|
| `payload_capture_max_bytes` | Truncates anything longer. Maximum `1048576` (1 MiB). |
| `payload_capture_redact_fields` | JSON keys stripped **before the write**, so a redacted value never reaches storage. |
| `payload_capture_models` | Capture only these models. Empty means all. |
| `payload_capture_virtual_key_ids` | Capture only these virtual keys. Empty means all. |

Redaction happening before the write is the important part: turning a field on later does not retroactively clean what is already stored, and turning it off does not expose history that was never captured.

The dashboard states all of this at the point of decision: the switch that turns capture on carries a summary of exactly what will be stored — the truncation limit, the retention window, the fields redacted before the write, and which models are captured — computed from the values currently in the form, so an unsaved edit is reflected in it.

### Why a payload panel is empty

The **Request** and **Response** panels in the log detail drawer are empty whenever no body was stored, and a body can be missing for three different reasons:

- payload capture was off when the request ran;
- capture was on, but the request's model or virtual key falls outside the allow-lists above;
- the payload's retention window has already passed. Payloads are kept for `payload_retention_hours`, which is deliberately shorter than the log row's own retention, so an old row keeps its metadata long after its body is gone.

The log row does not record which of the three applies, so the drawer names all three. A superadmin — the only role that can read this policy — sees the answer narrowed to the actual reason, because the screen reads the live setting for them. Every reader gets a link straight to this page's settings screen.

### Capture in the dogfooding profile

`integration/dogfood/gateway.toml` is the one profile shipped with capture **on**. It runs against fake and self-owned providers with no real user data, and payload visibility is the point of dogfooding the Logs screen, so the drawer shows real bodies out of the box. This is a local-stack exception, not a change to the shipped default — every other profile, and every fresh deployment, still starts with capture off.

## Retention

The two halves of the log expire on separate clocks:

- `retention_days` — how long log **metadata** is kept (1–3650 days).
- `payload_retention_hours` — how long **captured payloads** are kept (1–8760 hours).

Payloads cannot outlive the metadata they belong to. `payload_retention_hours` must not exceed `retention_days × 24`, and both the dashboard and the API reject a policy that breaks it — otherwise raw prompt content would survive past the point an operator meant it to expire.

### How expiry is enforced

There is no purge job. Rolter translates the policy into a ClickHouse **table TTL** (`alter table request_logs modify ttl …`, and the same for `request_payloads`), and ClickHouse drops expired parts itself during merges. Deletion is therefore eventual, not instant: a row past its TTL may survive until its part is next merged.

The TTL is written in two places, so a control plane that could not reach ClickHouse does not end up enforcing a policy different from the one it reports:

- **on update** — immediately after the policy is saved. If ClickHouse is unreachable the saved policy still stands and the API still returns `200`; losing the operator's setting because the log store was briefly down would be the worse failure.
- **at control-plane startup** — the stored policy is re-applied. This is what converges the two after an update that could not reach ClickHouse, and after a ClickHouse restored from backup or provisioned later, either of which would otherwise sit on the schema defaults (90 days / 7 days) indefinitely.

Re-applying an unchanged policy is a no-op, so the startup pass is safe on every boot. It runs in the background and never delays serving traffic.

## API

Both endpoints are **superadmin only**, and every update is audited.

```bash
curl -H "Authorization: Bearer $ROLTER_ADMIN_TOKEN" \
  https://control.example.com/api/v1/logging-settings

curl -X PUT -H "Authorization: Bearer $ROLTER_ADMIN_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
        "sample_rate": 0.1,
        "payload_capture_enabled": true,
        "payload_capture_max_bytes": 65536,
        "payload_capture_redact_fields": ["authorization", "api_key"],
        "payload_capture_models": [],
        "payload_capture_virtual_key_ids": [],
        "retention_days": 90,
        "payload_retention_hours": 168
      }' \
  https://control.example.com/api/v1/logging-settings
```

Send the full policy, not a patch. A successful update bumps `config_version`, so gateways pick it up on their next snapshot poll without a restart.

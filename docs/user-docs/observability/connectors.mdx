Rolter keeps its analytics in ClickHouse. A **connector** adds an outbound
destination on top of that: somewhere your telemetry is also shipped.

Connectors live under **Observability → Connectors** in the dashboard, and on
`/api/v1/connectors`.

<Note>
  Connectors are **strictly opt-in and off by default**. A deployment with no
  connectors has no egress path at all, and creating one does not turn it on —
  `enabled` is a separate switch. Air-gapped deployments are unaffected.
</Note>

## Kinds

| Kind | Status |
|---|---|
| `otlp_http` | Supported |
| Datadog, Prometheus remote-write, Langfuse | Planned |

OTLP is first deliberately. Every other sink here can be reached *through* an
OpenTelemetry Collector, so shipping OTLP makes the rest a collector
configuration change rather than more code in Rolter — that is also where
per-tenant routing belongs (see ADR-0026).

## How delivery actually works

A connector's `endpoint` is never called by Rolter directly. Rolter renders it,
along with every other enabled connector, into an OpenTelemetry Collector
config document at `GET /api/v1/connectors/collector-config` — one exporter and
one set of pipelines per connector. Point a collector at that URL (the OTel
Collector's confmap HTTP provider accepts `--config=http://...` sources,
bearer-authenticated the same as any other Rolter API call) and Rolter's own
`OTEL_EXPORTER_OTLP_*` export, which already targets that collector, fans out
from there.

This is why `sampling_rate` is a per-connector knob rather than a single global
one: each connector gets its own `probabilistic_sampler` processor in the
rendered document, so two connectors on the same deployment can sample
independently.

`managed_auth_secret` is decrypted and rendered as a literal bearer header.
`auth_secret_ref` instead renders as an `${env:...}` placeholder — the value
has to come from the collector's own environment, since Rolter never holds it.

The `ROLTER_TELEMETRY_ENABLED` kill switch wins over every connector: with it
off, the rendered document has no exporters at all, regardless of what is
enabled here.

### Reading the config from the dashboard

You do not have to `curl` for it. **Observability → Connectors** has a
**Collector config** button beside **Add connector**: it fetches the rendered
document, shows it in a scrollable pane, and copies it to the clipboard in one
click. Save it as your collector's config file — `infra/otel/collector.compose.yaml`
is the one the `docker/docker-compose.observability.yml` overlay mounts — or
point the collector straight at the URL with `--config` and reload it on a
schedule. With no connectors defined the panel says so instead of showing a
document with no exporters in it, because a collector running that would
deliver nothing.

## Fields

| Field | Meaning |
|---|---|
| `name` | Unique label for the connector |
| `kind` | `otlp_http` |
| `endpoint` | The `http(s)` URL telemetry is POSTed to |
| `enabled` | Off by default; nothing is sent until this is on |
| `sampling_rate` | `0.0`–`1.0`. `0.0` sends nothing, `1.0` sends everything |
| `auth_secret_ref` | A reference into your external secret manager |
| `managed_auth_secret` | Write-only bearer token, sealed before storage |

### Credentials are write-only

A `managed_auth_secret` is encrypted with the deployment KEK before it reaches
Postgres. It is **never** returned by the API and never appears in an audit
entry; responses carry only `auth_secret_configured`, a boolean. Storing one
requires the KEK environment variable to be set.

Editing a connector without resending the secret leaves the stored one in
place, so changing a sampling rate cannot silently drop the credential.

If you would rather Rolter never hold the secret at all, use `auth_secret_ref`
and keep it in your own secret manager.

### Endpoints go through the egress policy

A connector endpoint is a URL your deployment will POST to, which is the same
SSRF surface as a provider's `api_base` — so it passes the same
[egress policy](/configuration/egress) check, both when it is saved and again at
delivery time. A policy tightened after a connector was created applies to that
connector: a stored row is not a standing permission to egress.

## Test delivery

Every connector has a **Test** button, and a `POST /api/v1/connectors/{id}/test`
endpoint behind it.

It sends one OTLP request with an empty `resourceLogs` payload. That is a
well-formed request carrying no data, so it exercises the whole path — DNS, TLS,
the URL and the credential — without putting synthetic records into your
backend.

The result is stored as the connector's health (`healthy` / `unhealthy`, with a
timestamp and, on failure, a short reason) and shown in the connector list.
Failure reasons are the HTTP status or the transport failure class, never the
sink's response body — an error body can echo the credential it just rejected.

Test delivery runs whether or not the connector is enabled. That is the point:
check it before you turn it on.

<Tip>
  A connector that has never been tested shows `unknown` health rather than
  claiming to be healthy. If a connector reads `unknown`, nothing has verified
  it.
</Tip>

## Permissions

Connectors are a deployment-wide egress decision, so all four operations
require superadmin — the same level as the security settings, rather than
something delegable per organization.

Rolter can write a structured row to ClickHouse for every request it proxies. Each row captures everything you need to audit usage, track spend, and investigate issues — token counts, cost in USD, latency, error details, and the A/B variant that served the request. Writes are asynchronous and batched off the request path, so enabling logging adds zero latency for your users.

<Note>
  ClickHouse logging is entirely optional. If you don't need per-request records or cost tracking, you can skip this section and Rolter will still expose Prometheus metrics and traces.
</Note>

## Enabling logging

Set `clickhouse_url` in the `[logging]` section of your config file to point at your ClickHouse HTTP interface:

```toml rolter.toml
[logging]
clickhouse_url = "http://localhost:8123"
```

Logging is disabled when `clickhouse_url` is unset — there's no placeholder or no-op mode.

## What gets logged

Every proxied request writes one row to the `request_logs` table with the following fields:

| Field               | Type          | Description                                                                                                                           |
| ------------------- | ------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| `ts`                | DateTime64(3) | When the request **started** — the instant `latency_ms` is measured from                                                              |
| `request_id`        | String        | Unique request identifier, echoed in the `x-request-id` response header                                                               |
| `model`             | String        | The public model name the client requested                                                                                            |
| `provider`          | String        | The upstream provider that served the request                                                                                         |
| `target`            | String        | The specific upstream target within the provider                                                                                      |
| `status`            | UInt16        | HTTP status code returned to the client                                                                                               |
| `prompt_tokens`     | UInt32        | Prompt / input token count reported by the upstream                                                                                   |
| `completion_tokens` | UInt32        | Completion / output token count reported by the upstream                                                                              |
| `cost_usd`          | Float64       | Computed cost in USD (see [Cost tracking](#cost-tracking))                                                                            |
| `unpriced`          | UInt8         | `1` when the model had no price row, so `cost_usd` is unknown rather than zero (see [Unpriced traffic](#unpriced-traffic))            |
| `withheld`          | UInt8         | `1` when the provider answered and billed, but a guardrail or plugin refused delivery (see [Withheld responses](#withheld-responses)) |
| `usage_unknown`     | UInt8         | `1` when the upstream answered successfully but reported no token usage, so the zero tokens are unknown rather than free              |
| `latency_ms`        | UInt32        | End-to-end request latency in milliseconds                                                                                            |
| `ttft_ms`           | UInt32        | Time-to-first-token in milliseconds (streaming requests)                                                                              |
| `cached`            | Bool          | Whether the response was served from the upstream's prompt cache                                                                      |
| `error`             | String        | Error message if the request failed; empty on success                                                                                 |
| `variant`           | String        | Name of the A/B variant that served the request (blank when not using variants)                                                       |

<Note>
  `ts` is the moment the request began, so `ts + latency_ms` is when it finished. Rows written by a Rolter older than 1.0 have no `ts` of their own and fall back to the ClickHouse column default, which records the moment their **batch was flushed** — in that data a burst of requests shares one millisecond and ordering inside a batch is arbitrary. Only rows written by a current gateway carry the true request time.

`ts` is stored as `DateTime64(3)`, so requests that genuinely begin inside the same millisecond still share a timestamp. `GET /api/v1/analytics/invocations` therefore orders by `ts desc, request_id desc`: a tied pair keeps a stable, repeatable order, which is what stops a row appearing on two pages or on none.

</Note>

## Configuration reference

All `[logging]` fields except `clickhouse_url` have sensible defaults and are optional:

```toml rolter.toml
[logging]
clickhouse_url = "http://localhost:8123"  # required to enable logging

# flush when batch reaches this many rows (default: 1000)
batch_max = 1000

# also flush partial batches at least this often, in milliseconds (default: 1000)
flush_ms = 1000

# bounded queue capacity; rows are dropped and counted when full (default: 10000)
queue_capacity = 10000
```

<AccordionGroup>
  <Accordion title="clickhouse_url">
    **Type:** String · **Default:** unset (logging disabled)

    Base URL of your ClickHouse HTTP interface, e.g. `http://clickhouse:8123`. Rolter uses the HTTP interface — not the native TCP protocol — so no special driver is required. Logging is disabled entirely when this is unset.

  </Accordion>

  <Accordion title="batch_max">
    **Type:** Integer · **Default:** `1000`

    Rolter accumulates log rows in an in-memory batch and flushes to ClickHouse once the batch reaches this size. Larger values reduce ClickHouse insert pressure but increase memory usage and the number of rows lost if the gateway crashes before a flush.

  </Accordion>

  <Accordion title="flush_ms">
    **Type:** Integer · **Default:** `1000`

    Maximum time in milliseconds between flushes. Even if `batch_max` hasn't been reached, a partial batch is flushed at least this often. At the default value of `1000`, log rows appear in ClickHouse within about a second of the request completing.

  </Accordion>

  <Accordion title="queue_capacity">
    **Type:** Integer · **Default:** `10000`

    The bounded in-memory queue between the request path and the background log writer. When the queue is full (e.g. ClickHouse is slow or unreachable), incoming rows are dropped rather than blocking the request. Dropped rows are counted by the `rolter_log_dropped_total` Prometheus counter so you can alert on them.

  </Accordion>
</AccordionGroup>

## Cost tracking

The `cost_usd` field on each log row is computed from the `[[model_prices]]` entries in your config. You define the input and output price per million tokens for each model, and Rolter calculates the cost automatically:

```toml rolter.toml
[[model_prices]]
model = "gpt-4o"
input_per_mtok = 2.5
output_per_mtok = 10.0
cached_input_per_mtok = 1.25   # optional; defaults to input_per_mtok when absent
```

<Steps>
  <Step title="Define prices">
    Add a `[[model_prices]]` block for each model you want to track. You can define prices for managed models (OpenAI, Anthropic) and self-hosted models alike.
  </Step>
  <Step title="Rolter computes cost per request">
    After each completed request, Rolter multiplies the upstream-reported token counts by your configured rates. Cached input tokens use `cached_input_per_mtok` when set, falling back to `input_per_mtok`.
  </Step>
  <Step title="Query spend in ClickHouse">
    Rows without a matching model price record `cost_usd = 0` **and `unpriced = 1`** — they still appear in logs, they just don't contribute to spend reports until you add a price.
  </Step>
</Steps>

### Prices are yours, not ours

Rolter ships no pricing catalog and never fetches one. Every rate comes from
your `[[model_prices]]` entries, or from the **Pricing override** section of a
model's sheet in the dashboard, which writes the same rows. That is deliberate:
published list prices go stale, and most deployments have a negotiated rate, a
committed-use discount or a self-hosted model whose real cost is a GPU bill.
Rolter multiplies the tokens it counted by the number you gave it.

The dashboard's pricing section links here for that reason — it is the answer
to "where does this number come from", and the answer is "from whoever typed
it".

### Unpriced traffic

A zero `cost_usd` is ambiguous on its own: it means either "this request cost nothing" or "we have no price for this model". The `unpriced` column tells them apart, so a spend total can say when it is incomplete rather than presenting a partial figure as final.

```sql
-- how much of a window's spend is missing, and which models are responsible
select countIf(unpriced = 1)          as unpriced_requests,
       uniqIf(model, unpriced = 1)    as unpriced_models,
       round(sum(cost_usd), 6)        as known_spend
from request_logs
where ts >= now() - interval 24 hour;
```

The dashboard reports the same two figures on `GET /api/v1/analytics/summary` (`unpriced_requests`, `unpriced_models`) and `GET /api/v1/analytics/by-model` (`unpriced_requests`), and shows a notice above the spend tile whenever a window contains unpriced traffic.

The flag is exposed **per invocation** too, not only in those summaries: every row from `GET /api/v1/analytics/invocations` carries `unpriced` beside its `cost_usd`, so a single request can be read the same way the totals are.

The **LLM Logs** screen does the same per request: a row whose model has no price shows a muted **—** with an explanation on hover instead of `$0.0000`, because a zero there claims the request was free. It reads the row's own `unpriced` flag to decide, which is the judgement the gateway made against the price catalogue **as it was when the request was served**. That matters once prices change: a request served before you priced a model stays unpriced in the log even after you add the price, and one served under a price you later delete keeps the cost it was actually charged.

The **Models** screen names the cause. A model with no price row shows **no price set** in the in/out price column instead of a dash, and an **Unpriced** filter chip above the table counts them and narrows the list to exactly those models — so the fix for an incomplete spend total is one click from the number that reported it. If the price catalogue itself cannot be read, the column falls back to plain figures rather than reporting every model as unpriced on no evidence.

Unpriced traffic accrues **no spend**, so it cannot exceed a budget no matter how much is served — budgets simply do not apply to a model you have not priced. `unpriced_policy` decides what to do about that:

```toml
unpriced_policy = "block"   # ignore (default) | warn | block
```

| policy   | behaviour                                                                                                                                                                 |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ignore` | Serve it and accrue nothing. Budgets silently do not cover it.                                                                                                            |
| `warn`   | Serve it, but log the model once per hour and treat any budget covering the window as an incomplete accounting.                                                           |
| `block`  | Refuse at admission with `402` (`model_unpriced`), naming the model. Nothing is forwarded, so no upstream tokens are spent on traffic that would never have been counted. |

`ignore` is the default so that upgrading cannot start refusing traffic for a deployment that has not priced its models yet — which, on a fresh install, is all of them. Once your price catalogue is complete, `block` costs nothing and closes the gap; the [unpriced-request count](#unpriced-traffic) above is how you tell when you are there.

<Note>
  The built-in `fake-llm` model is answered by the gateway itself, before any price is looked up, so `block` never takes away the model you smoke-test a deployment with.
</Note>

Two Prometheus counters track this: `rolter_unpriced_served_total` (requests served with no price — non-zero means your spend figures are a floor) and `rolter_unpriced_blocks_total` (requests refused by `block`).

Rows written before the `unpriced` column existed default to `0`. That under-reports the unpriced share of historical data rather than inventing one.

### Withheld responses

An output [guardrail](/security/guardrails) with `block`, or a `post_response` [plugin](/configuration/plugins) that blocks, runs **after** the provider has generated the answer. The caller gets a `403` and never sees the answer. The provider still charged for it, so Rolter bills it anyway:

- The row's `status` is `403` (what the caller received) and `withheld` is `1`.
- `prompt_tokens`, `completion_tokens` and `cost_usd` are the provider's figures, and they count toward budgets and token rate limits like any delivered request.
- `error` names the policy, either `guardrail_blocked: <rule name>` or `plugin_blocked: <plugin reason>`. The rejected answer itself is never stored, even with payload capture on.

Usage is read from the provider's response **before** any guardrail, plugin or PII sanitizer runs. A plugin that rewrites or strips the `usage` object changes what the caller sees, not what you are billed.

A response-cache hit that a rule blocks is logged with `cache_hit = 1`, `withheld = 1` and zero cost, since nothing was generated upstream for it. The original miss was billed when it happened.

To see what blocked output is costing you:

```sql
select sum(cost_usd)            as withheld_spend,
       count()                  as withheld_requests
from request_logs
where withheld = 1 and ts > now() - interval 30 day;
```

`rolter_withheld_responses_total` counts the same refusals in Prometheus. A sustained rate usually means a prompt is steering the model into output your policy forbids, and you pay for every attempt.

`usage_unknown = 1` marks a different gap: the upstream answered but reported no usage at all, so the row's zero tokens and cost are unknown rather than free. Most often it is an OpenAI-style stream sent without `stream_options: {"include_usage": true}`. It is also set on a `502` whose upstream answered and then failed to deliver the body the gateway was reading (a reset, a truncated response): the provider may have billed an answer nobody received. Rows written before these columns existed default to `0`.

## Paging the invocation log

`GET /api/v1/analytics/invocations` returns one page of requests plus the cursor that resumes it:

```json
{ "data": [ /* newest first */ ], "next_cursor": "2026-07-19 12:00:01.000|req-1" }
```

Ask for the next page by handing that value straight back as `cursor`:

```bash
curl -H "Authorization: Bearer $ROLTER_ADMIN_TOKEN" \
  "https://control.example.com/api/v1/analytics/invocations?limit=50&cursor=2026-07-19%2012%3A00%3A01.000%7Creq-1"
```

The cursor is a position in the list's sort key — `(ts, request_id)`, newest first — not a row number, and this is what makes paging a live log correct. `request_logs` is written continuously by the gateway, so requests land above the window while you read: a row offset would count them in and either serve you a row you already saw or skip one entirely. A keyset bound cannot be moved by rows above it, so every request that existed when you started paging is returned exactly once. `request_id` breaks ties, so two requests logged in the same millisecond still have one order.

Treat the cursor as opaque and pass it back unchanged. `next_cursor` is `null` only for an empty page; a short page still carries one, so stop when a page comes back with no rows. `limit` is clamped to `1..=200` and defaults to 50.

<Note>
  Every filter — `since`, `until`, `model`, `key`, `business_unit`, `customer`, `status`, `request_id`, `trace_id` — must be repeated with the cursor, since it is the same query resumed rather than a stored server-side page.
</Note>

The **LLM Logs** screen pages the same way. **Next page** follows the cursor the current page returned and **Previous page** goes back to the one it came from, so a page you return to holds the requests it held before, however much traffic arrived in between. Only the first page follows live traffic while **Streaming** is on; later pages stay fixed on their cursor. Changing a filter starts again from the newest request, and a page after a full last page reads as the end of the log with a **Back to newest** button.

## Finding one request by its id

Every gateway response carries `x-request-id`, and the same id is the row's `request_id`. When a client reports a failed call, that id takes you straight to it:

```bash
curl -si https://gateway.example.com/v1/chat/completions ... | grep -i x-request-id
# x-request-id: 3f2c9a1e-...

curl -H "Authorization: Bearer $ROLTER_TOKEN" \
  "https://control.example.com/api/v1/analytics/invocations?request_id=3f2c9a1e-..."
```

The answer is that one row, with its status, error, tokens, cost, latency and — if your role may read them — the captured bodies. `trace_id` looks a request up by its W3C trace id the same way, for when you start from a span in your tracing backend instead. Without a `since`, a lookup by either id searches every row still retained rather than the default last 7 days, so an older request is found rather than answered with an empty page. The lookup obeys the same visibility as the rest of the log: an id from a project you cannot read returns nothing.

## Built-in dashboard

The Rolter control plane's dashboard queries ClickHouse directly to give you usage, spend, latency percentiles, and error rates — all sliced by model, project, and virtual key. No extra ETL or data pipeline is needed: the rows Rolter writes are the source of truth for the dashboard.

<Tip>
  Use the `variant` column to run A/B cost analyses. If you have two variants serving the same logical model (e.g. `gpt-4o` vs `claude-sonnet`), you can compare average `cost_usd` and `latency_ms` per variant directly in ClickHouse or your BI tool.
</Tip>

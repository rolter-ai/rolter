The dashboard is the control plane's web UI. It is served by `rolter-control` on the same port as the API (`4001` by default) and works fully offline: it ships no runtime fonts, scripts or images from a CDN.

## Signing in

Open the control plane's address in a browser. You will see one of three things:

- **A password form** — the deployment has local accounts. Use the e-mail and password an administrator created for you, or the ones you chose when accepting an invitation link.
- **"Continue with …" buttons** — the organization registered an identity provider ([Single sign-on](/security/single-sign-on)). Password sign-in may be turned off alongside them.
- **An e-mail-only prompt** — the control plane is running in _open mode_ with no admin token and no accounts. Anything you enter opens the dashboard; there is no session to protect. This is meant for a first local run only.

<Note>
  A control plane started from `rolter.toml` alone, with `ROLTER_ADMIN_TOKEN` set but no `--database-url`, also shows the e-mail-only prompt, because it has no accounts to sign in to. The request log, usage and provider health still require the admin token there, and the dashboard has no field to enter it, so the Dashboard, Logs and Health screens report that you are not signed in. Read them with the token over the API (`curl -H "Authorization: Bearer $ROLTER_ADMIN_TOKEN" .../api/v1/analytics/invocations`), or give the control plane a database. Letting the dashboard take the token is tracked in [#1909](https://github.com/rolter-ai/rolter/issues/1909).
</Note>

Your session is re-checked every time the dashboard loads. If it has expired, you are returned to the sign-in screen with a note saying so rather than a page full of failed requests.

The language switcher sits at the bottom of the rail, and on the sign-in card, so you can pick English or Russian before you have an account.

## Getting started

A fresh deployment opens the Dashboard on a **Getting started** card: the four steps between an empty control plane and a client calling Rolter, plus the request that client would send. That request is addressed to the base URL saved under [Client Settings](/configuration/client-settings#base-url), and shows a prompt to save one when none is saved or your role cannot read it. The dashboard's own `/gw` proxy requires a dashboard session, so it is never offered to a client outside the dashboard.

1. **Make a call with no credentials.** The gateway ships a built-in `fake-llm` model that answers without an upstream or a provider key, so the Playground works before anything is configured. You do not need a key of your own either: the Playground mints one for itself, and for a project with no routes yet that key reaches `fake-llm` and nothing else.
2. **Connect a provider.** The key is sealed in the store and never shown again.
3. **Add a route** — the model name your clients ask for, and where it lands.
4. **Mint a virtual key.** Clients authenticate with it rather than with your provider key, which is what makes per-key budgets and logs possible.

Every step runs inside a project. When the team selected in the scope switcher has no project yet, the card shows a **Create project** button that opens the same dialog as the **+** beside Project in the switcher, and selects the new project once it is created. With no team yet, the card asks you to add an organisation and a team in the switcher first. Creating a project takes the admin role, so for other roles the button is disabled and names the role it needs.

Each step is ticked from the deployment itself, not from a checklist kept in your browser: a step reads as done when the row exists, so work another administrator did shows up on reload. A step whose form your role may not open is shown as a disabled button naming the role it needs, rather than a link into a screen that would refuse you.

The card is for whoever sets the deployment up. If your role can add none of a provider, a route or a virtual key (a member or a viewer, typically), the Dashboard opens straight on its traffic panels and the card is not shown at all. The same happens when your role may not read the providers, routes or keys it would tick off. Neither case is reported as an error.

**Dismiss** hides the card and leaves a **Getting started** button in its place, so it is never gone for good. It retires itself once the deployment has both a provider and traffic — traffic on its own can be a single Playground call, which is step one.

## The overview figures

The Dashboard's first row is four figures for the last 24 hours: requests, spend, average latency and error rate. Under the error rate, the number of failed requests turns red once errors pass 1% of requests and stays grey below that. None of the four carries an up or down arrow, because none of them is compared with an earlier window.

Average latency and error rate are measured over the window's requests, so a window with none has nothing to average. Both read **—** with _No requests in this window_ under them, instead of `0 ms` and `0.00 %`, which would read as a measurement of a quiet deployment. The request count and the spend stay real zeros. The line under the spend chart's title names the currency the deployment is configured in, the same one the amounts are written in.

Without ClickHouse the Dashboard has no traffic to count. It shows one note in place of the figures and charts, naming `CLICKHOUSE_URL` as the setting to add. The note is information about the deployment rather than an error, so it offers no retry and stays on screen until the setting changes. The setup checklist above it is unaffected.

"Last 24 hours" means the 24 hours before each read, not before you opened the page. The Dashboard reads again on its own, so a tab left open for an afternoon still reports a single day, and so does the refresh button in the header.

The window picker above the cards switches the figures and charts to another [reporting window](/observability/logs-and-cost#time-windows), kept in the address as `window=7d`. **Saved views** next to it saves the window under a name and applies it again later; see [Saved views](/observability/logs-and-cost#saved-views). **Recent requests** always lists the latest requests, whatever window is picked.

Under the figures, the traffic share and the requests-by-model bars rank models by request count, busiest first, and colour them from the same sequence, so a model is one colour in both cards. The bars show the six busiest models; the traffic share shows those six and rolls the rest into one _Other_ slice. The caption under the share's total agrees with it, in the plural forms of the dashboard's language.

**Recent requests** lists the eight latest requests with their time, model, status and latency. The 24-hour window crosses midnight, so a request from another day shows its date under the clock; one from today shows the clock alone. Each row opens that request in [LLM Logs](/observability/logs-and-cost). On a phone the four columns share the card's width without scrolling.

## The left rail

Everything lives under one of these groups. Screens you cannot read with your role are hidden; superadmin-only screens are hidden for everyone else.

| Group                                        | What is inside                                                                                                                                                                                                                                                      |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Playground**                               | Send chat, embedding, image, audio or realtime requests through the gateway with one of your virtual keys.                                                                                                                                                          |
| **Observability**                            | Dashboard (traffic, spend, latency, error rate), LLM Logs, MCP Logs, Connectors, Logs Settings.                                                                                                                                                                     |
| **Models**                                   | Model Catalog, Providers, Provider Groups, Budgets & Limits, Routing Rules, Complexity Router, Provider Health, Pricing Overrides, Model Settings.                                                                                                                  |
| **MCP Gateway**                              | MCP Catalog, Library, Tool Groups, Auth Sessions, OAuth Grants, MCP Settings.                                                                                                                                                                                       |
| **Plugins**                                  | Webhook plugins in the request/response pipeline.                                                                                                                                                                                                                   |
| **Alerting**                                 | Channels, Rules, History. See [Alerting](/observability/alerting).                                                                                                                                                                                                  |
| **Governance**                               | Virtual Keys, Users, Teams, Business Units, Customers, User Provisioning (SCIM), Single sign-on, Roles & Permissions, Access Profiles, Audit Logs.                                                                                                                  |
| **Guardrails**                               | Rules and providers for content, PII and safety checks.                                                                                                                                                                                                             |
| **Cluster Config**                           | The gateways that poll this control plane. A gateway names itself from `ROLTER_NODE_ID`, else `HOSTNAME`, else the host's own name, and logs which one it used at boot. Set `ROLTER_NODE_ID` when several gateways share a host, or they all heartbeat as one node. |
| **Adaptive Routing**                         | Live scores from gateways on the adaptive strategy, and its settings.                                                                                                                                                                                               |
| **Prompt Repository**, **Skills Repository** | Versioned prompt templates and agent skills shared across the org.                                                                                                                                                                                                  |
| **Settings**                                 | Client settings, compatibility, the effective config viewer, security, your own virtual keys, performance tuning, feature flags.                                                                                                                                    |

The effective config viewer also exports the deployment's configuration as an importable `rolter.toml` — see [Config Export](/configuration/config-export).

The search box at the top of the rail filters the entries by name; press `/` from anywhere to jump into it. Matching a group's own name keeps everything filed under it, and a query that matches nothing says so rather than leaving the rail blank.

### Experimental entries

Some entries carry a small **Experimental** badge beside their name. That marks a subsystem which is usable but not yet settled: it may change shape, or be removed, in a minor release, and it is exempt from the compatibility promise the rest of the surface makes. Hover the badge to read what specifically is unfinished, in the language the dashboard is set to. When the rail is folded to icons the badge becomes a small dot on the entry's icon, and hovering the entry names it.

The list comes from the running control plane, not from the browser, so it is always the truth about the build you are using: an entry loses its badge as soon as you upgrade to a release where that subsystem has settled. Entries with no badge are stable.

## Keyboard shortcuts

| Key                                  | What it does                                                                                                                            |
| ------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------- |
| `⌘K` (`Ctrl-K` on Windows and Linux) | Opens the **command palette**.                                                                                                          |
| `/`                                  | Puts the caret in the rail's search box. Ignored while you are typing in a field, so a slash in a model name or a prompt stays a slash. |
| `?`                                  | Opens **Keyboard shortcuts**, the list of everything on this table. Ignored while you are typing, for the same reason `/` is.           |
| `Tab`, from the top of the page      | Reveals **Skip to content**, which jumps focus past the rail into the screen.                                                           |

You do not have to memorise the table: the palette prints `⌘K` beside its own
search field, the rail's search box prints `/`, and `?` shows the whole list.
Each shortcut is printed with the key your keyboard actually has — `⌘` on a
Mac, `Ctrl` everywhere else.

There is no keyboard required to find them either. The keyboard icon in the
rail's footer, beside the magnifier that opens the palette, opens the same
**Keyboard shortcuts** sheet, and names the key it stands in for when you hover
it. It is there at every width, including the drawer the rail becomes on a
phone.

The command palette searches two things at once. Screens first: every entry in
the rail, matched loosely, so `rr` finds Routing Rules and `audlog` finds Audit
Logs. Then records — virtual keys, providers and routes in the current scope,
by name — each labelled with what it is, opening the screen that lists it. With
nothing typed, the palette offers the screens you opened last.

Paste a request ID or a trace ID and, when nothing else matches it, the palette
offers **Open request … in LLM Logs**, which opens the log on that id. See
[Finding one request by its id](/observability/logs-and-cost#finding-one-request-by-its-id).

Arrow keys move the selection, Enter opens it, Escape closes the palette and
puts focus back where it was. The magnifier at the bottom of the rail opens the
same palette with the mouse. The palette only searches what your account may
read, and only the record lists the dashboard already loads — it is not a
full-text search over logs or requests. An id is looked up exactly, not searched.

## The scope switcher

Most screens show data for one **organization → team → project** chain. Open the account menu at the bottom of the rail to change any of the three, create a new one with the **+** button, or delete the selected one. The choice is remembered per browser; a fresh browser starts on the first organization you belong to.

Screens that are deployment-wide (feature flags, security, performance, cluster) ignore the scope.

## What a disabled control means

A greyed-out **Add**, **Delete** or toggle carries a tooltip naming the role the action needs (for example _Requires the Admin role_). The dashboard asks the control plane what your account may do and disables the rest up front, instead of letting you click and read a "forbidden" error afterwards. See [Roles and permissions](/security/rbac).

## Refresh and live data

The refresh button in every screen header re-reads everything on the screen. Screens that stream (LLM Logs, MCP Logs, Adaptive Routing) update on their own and show when they last did.

MCP Logs is open to every role and narrowed to your scope: you see the calls of the organizations, teams and projects you hold a role in, plus every call made through your own MCP sign-ins. A call's arguments and result are shown to members and admins, and to viewers on a project that allows it; for anyone else the call opens with a note that they are hidden for your role. **My calls** narrows the list to the calls made under your own account.

The Dashboard's **Recent requests** card is labelled **Live** once its first read has answered, and asks for new requests every 15 seconds. The four figures and the charts above it are aggregates over a day, so they are read once a minute. Both pause while the browser tab is hidden and read again when you come back.

Every card on the Dashboard reads for itself: the four figures, the spend chart, the traffic share, requests by model and the recent requests. While a card's first read is out it shows placeholders in its own shape, and it never says there is no traffic or nothing logged about a read that has not answered. If that read fails, only that card shows the error, with its own **Try again**, and the cards that loaded stay as they are. A card whose first read failed stops refreshing until you press its **Try again** or the header's refresh button. The traffic share and requests by model are drawn from one read, so when that read fails the traffic share shows the error and requests by model says it reads the same data, rather than repeating it.

When every read fails at once, because the control plane is down or ClickHouse refuses all of them, the Dashboard shows one error in place of the cards instead of five, naming the analytics and quoting the control plane's message. Its **Try again** reads all of them again. The setup checklist above it stays.

If a refresh fails after a card has shown data, the card keeps what it has and says so underneath it, in red: _Refresh failed at 15:34:56, retrying_, until a refresh succeeds. The Recent requests card says it in its label instead, where **Live** gives way to the same sentence. **Live** is only shown while the last read of the card succeeded: while the first read is still out, the label reads **Loading**, and if it fails, the label reads _Load failed at 15:34:56_.

LLM Logs says **Streaming** only after a read that succeeded. While the first page loads, its toolbar says it is loading, and when a read fails it gives the time of the failure instead. If the very first read fails, the screen stops refreshing and keeps the error on screen until you press **Try again**. If a later refresh fails while rows are already showing, the rows stay, and the toolbar reads _Refresh failed at 15:34:56, retrying_ until a refresh succeeds or you pause the stream.

## The gateway status in the header

Next to the refresh button, every screen header shows whether the gateway is taking traffic. The dashboard asks the gateway's `/readyz` every 30 seconds, through the control plane, and the pill shows what came back:

| Pill                   | Meaning                                                                                                                   |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------- |
| gateway healthy        | The control plane reached the gateway, and it is taking traffic. The green dot pulses.                                    |
| gateway draining       | The gateway was drained from the Cluster screen. It finishes the requests in flight and takes no new ones.                |
| gateway unreachable    | The control plane cannot reach the gateway at `ROLTER_GATEWAY_URL`.                                                       |
| gateway status unknown | The check got no answer the dashboard can read, for example because the browser lost its connection to the control plane. |
| checking gateway       | The first check has not come back yet.                                                                                    |

Hover the pill to see when it was last checked. One failed check does not change it: the pill keeps the last answer, stops pulsing, and says when that answer arrived. A second failed check turns it to unknown. Checks pause while the browser tab is hidden, and the refresh button checks again along with everything else.

Every role sees the same pill. It reports the gateway the control plane forwards to: with several gateway replicas behind one address it means one of them answered, and it cannot tell whether a gateway has picked up the latest configuration. The Cluster screen, for superadmins, lists every node, whether it is live, and whether it runs the current configuration.

## Models, strategies and targets

**Models → Model Catalog** lists every model the gateway serves, the ones shipped in `rolter.toml` and the ones created in the dashboard alike. Each row shows its route's strategy as the identifier you would write in the config file, and how many targets the route spreads traffic across. A strategy with a caveat says so under its name: `precise_cache_aware` and `lmcache_aware` need a cache-telemetry source on their providers, which only a provider defined in `rolter.toml` can carry today (see [Cache-aware routing](/concepts/cache-aware-routing#precise-vllm-and-lmcache-modes)), and `adaptive` is governed by the deployment-wide adaptive-routing policy.

Open the target count to see each target: its provider, the model id sent upstream, and its weight. Only `weighted`, `pipeline` and `adaptive` read weights, so only those routes show each weight as a share of traffic. Under any other strategy the list says the weights do not split traffic. Where the health rollups are available (they need ClickHouse), each target also shows its uptime over the last 7 days against a 99% SLA, the row names how many targets are below it, and a target nothing has observed yet says **no health data**.

**Models → Routing Rules** shows each route as a card and follows the same rule: a share and a bar per target only under `weighted`, `pipeline` and `adaptive`, and a note that the weights do not split traffic under any other strategy. The cards do not show target health; Model Catalog and the Health screen do.

**+ Add model** takes the name clients will send, the strategy, and one or more targets. **+ Add route** on Routing Rules opens the same sheet, so a route is created the same way from either screen. Editing a model shows every target and saves only the lines you changed. The strategy is fixed once the model exists, for now ([#2208](https://github.com/rolter-ai/rolter/issues/2208)).

## When part of a screen fails to load

Some screens read one record per row — the Complexity Router asks for each route's policy separately. If a row's read is delayed or refused, that row is not reported as empty. It is listed under **Policy could not be read**, with the reason from the control plane and a **Try again** button, and it offers no editor: writing a policy over one you were never shown is worse than waiting. Rows whose read is still in flight sit under **Checking for a policy** as placeholders, and the summary line counts only the rows that actually answered.

Routing Rules reads each route's targets separately as well. A card whose targets are still on the way shows placeholders where they will be. A card whose read failed shows the reason and a **Try again** button in their place. Neither says **No targets yet** or counts zero targets. The route count at the top of the screen appears once the route list has answered, so a slow or refused load is never reported as an empty project.

Reading a route's complexity policy takes the same permission as reading the route itself, so a read-only account sees every policy it can see routes for; changing one still takes an admin. An account that may not read the route at all is told it does not have access rather than being shown the route as unconfigured.

## Reading structured output

Anywhere the dashboard shows a payload — a request or response body in LLM Logs and MCP Logs, an audit entry's detail, the effective config, a model's config preview, the collector document, a copy-as-code snippet — it renders in a shared code block: syntax highlighted for its language, scrollable sideways rather than wrapped mid-token, reachable with the Tab key, and with a copy button in its corner. Highlighting is bundled with the dashboard, so it works with no internet access.

A very large payload is shown without colour rather than kept waiting for it.

## The Playground's key

The Playground authenticates to the gateway like any other client, with a virtual key — but you do not paste one. Opening the screen mints a **session key** for the project you have selected:

- It is scoped by the control plane to the models that project routes, so it can never reach a model you could not already reach. A project with no routes yet gets a key for the built-in `fake-llm` alone, so the first message gets an answer before any provider or route exists. The bar says so and links to **Routing Rules**; once the project routes a model, **Renew key** mints a key that reaches it.
- It lives 30 minutes. The bar shows when it expires, and **Renew key** mints a fresh one rather than extending it. When there is no key to renew, the same button reads **Mint key**.
- It is held in your browser's memory only. Closing the tab ends it; nothing is written to browser storage.
- It appears on **Virtual Keys** and in **Settings → My Virtual Keys** labelled _Playground_, so a key with a half-hour life is recognisable as one the screen issued. It expires on its own — there is nothing to clean up.

A new key takes a few seconds to reach the gateway, which learns about keys on its next config poll (every 5 seconds by default, `ROLTER_SNAPSHOT_POLL_SECS`). Until then the model picker says it is waiting and keeps the built-in `fake-llm` selected, asking again with a growing pause for about ten seconds. Once the gateway accepts the key, the picker lists what the gateway serves and selects the first route in it.

If the gateway never accepts the key, the picker falls back to the configured routes and says so. That list leaves out routes the control plane is not sending to the gateway (the **Providers** screen lists them as config entries not being served as written), says how many it left out, and opens on a route that is served. When rolter cannot tell which routes those are, it keeps `fake-llm` selected rather than guess.

If the gateway refuses the key, the badge reads **Rejected** rather than **Active**, and the bar suggests minting a fresh one or pasting one the gateway accepts.

The bar says one thing at a time. When the screen cannot mint a key itself, it says why and opens **Use a specific key** for you:

- **No project selected.** Pick one in the scope switcher, or paste a key.
- **Your role cannot mint.** Minting takes the **Member** role in the project. A **Viewer** is not sent into a refusal: the Playground does not try, **Mint key** says which role it takes, and the bar asks for a key someone gave you.

Sign in first — minting is a per-account action, and a deployment running without accounts has none to mint against.

**Send**, and the run buttons on the other tabs, stay disabled until there is a key the gateway accepts: while a new key is on its way, when there is none, and when the gateway refused the one in hand. Hover the button to see why. A gateway that is running on its own with no keys configured, as the no-database `rolter easy-up` does, answers requests without one; the Playground checks for that once and says so, and then sends without a key.

To test one particular key on purpose — a customer's, or one you are about to rotate — open **Use a specific key** and paste it. A pasted key is used exactly as given, with no expiry of rolter's choosing, until you replace it or mint a session key.

## The chat composer

**Enter** sends the message and **Shift+Enter** adds a new line, so a prompt can run over several lines. The box grows with the draft up to about six lines, then scrolls. The **Enter** that confirms a candidate in an input method editor, as when typing Japanese, Chinese or Korean, belongs to the composition and does not send.

Each chat column keeps its conversation, and any draft you have not sent, while you visit another tab. So do the other tabs: Embeddings keeps the texts you edited and their projection, Image keeps the prompt and the generated images, and Audio keeps the text to synthesize and the clip, or the uploaded file's transcript. A clip that is playing pauses when you leave. A request still on its way when you leave lands where it started, so an image you are waiting on is there when you come back, and coming back never sends it again. Nothing is saved: all of it lives in the page, so reloading or leaving the Playground clears it.

Realtime is the exception. Leaving its tab closes the session and clears the event log, because a session kept alive under a tab you are not looking at would hold a WebSocket open. The tab says so above the session.

A screen reader hears each finished reply once it has arrived, as the model's name followed by the reply, and hears a failed send's error as an alert. Every field has a name of its own, not only a placeholder. Each column's conversation is a region named after its model: press Tab to reach it, then the arrow keys or Page Down to scroll a long reply. The buttons a column repeats say what they act on, as in **Send to** a model and **Copy as code for** a model. In a comparison they also carry the column's number, and **Remove column** carries its number and model, so two columns holding the same model stay apart. On Embeddings each row's **Remove text** button carries the row's number.

## Markdown in the Playground

Model replies render as markdown: headings, lists, tables, inline code, and fenced code blocks highlighted per their language tag with a copy button of their own. Use the **¶** button in the column header to switch to raw output when the question is exactly what the model emitted, including stray delimiters and whitespace.

Replies are never treated as markup. HTML tags in a reply show as the characters they are, and an image in a reply is listed by its alt text instead of being fetched — nothing in a model reply causes the dashboard to reach the network.

## On a phone or a tablet

| Screen width   | Navigation                                                                                                                                  |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| Below 768 px   | The rail is a drawer. Open it with the **☰** button in the screen header; close it with the scrim, the Escape key, or by picking a screen. |
| 768 – 1023 px  | The rail starts folded to icons. Hover or focus an icon for its name; the collapse toggle expands it.                                       |
| 1024 px and up | The full rail, collapsible, and resizable by dragging its right edge. The width you choose is remembered.                                   |

Tables that are wider than the screen scroll inside their own frame, and forms that open as side sheets take the full width on a phone. On a phone a side sheet's buttons stack: Cancel and the main action share the bottom line, and any other action, such as testing a provider's connection, sits above them. The screen area below the header is a scroll region you can Tab to, so a long screen can be read with the keyboard alone.

A dialog taller than the window, on a short laptop screen or at 200 % zoom, opens with its title and close button on screen and scrolls. The longer form dialogs, such as editing a guardrail rule, a plugin or an MCP server, keep their buttons on screen too and scroll only the fields in between.

## With a screen reader

The list screens (Virtual Keys, Users, Model Providers, Provider Groups, the Model Catalog, Alert History, MCP Logs, OAuth Grants and Auth Sessions) are tables to a screen reader, named after the screen, so table navigation works and each cell is read with its column header. A column you can sort says whether it is sorted ascending, descending or not at all. The column of row buttons has no visible heading and is announced as **Row actions**; on Auth Sessions the two button columns are **Renew** and **Revoke**. On MCP Logs that column is **Details**: each row's button is named after the tool, the server and the time of the call, and it opens the call's arguments and result. Focus moves into the details panel, and Escape or the panel's close button returns it to that button.
